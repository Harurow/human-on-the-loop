# ADR-012: 複数ファイルにまたがる状態更新は「更新開始/更新完了」で囲み、再開時は種別ごとに冪等にやり直す

**状態**: Accepted（2026-09-06）／**関連**: 回帰 D-8〜D-10、ADR-001・ADR-008

## 文脈
承認（log → requirements.md → sha256 → state → 遷移）、承認リセット（log → state → requirements.md → 遷移）、フェーズ遷移（state → log → commit → 報告）は、いずれも複数ファイルを順に書き換える。途中でセッションが切れた場合の復旧規則が、02「承認手続きの途中中断」・Step 4「文脈復元」の遷移報告補完・「done の不変条件」・イテレーションの「phase が既に hearing なら」など**場面ごとに別々に**書かれ、45〜50周で繰り返し欠陥が出た（R45-2・50周 MINOR-6 ほか）。ユーザーの最優先要望「途中で止まっても指示を取りこぼさず正しく再開できること」の中核。

## 決定
- 複数ファイルにまたがる更新は**共通手順「状態更新」**で行う: log.md に `更新開始: <種別>` → 種別ごとに固定した順序で**冪等な**書き込み → `更新完了: <種別>`
- 種別は3つ（フェーズ遷移・承認・承認リセット）。Step 6・02 の承認手順・承認リセットはこの手順への参照になる
- **再開時の復旧は Step 4 の最初の検査**: 完了の無い開始があれば、その種別の書き込みを最初からやり直す。これが唯一の途中クラッシュ復旧手段
- 場面ごとのクラッシュ規則（上記4つ）は削除する

## 理由
- 復旧が「ログを読んで状況を推理する」形だと、場面が増えるたびに規則が増え、規則同士が矛盾する（実際に起きた）
- 「開始と完了で囲む＋各書き込みが冪等」なら、復旧は「完了が無ければやり直す」だけで済み、**どの手順のどこで切れても同じ判定**になる
- 冪等性の担保はコストが小さい（既に済んでいれば触らない、を各項目に書くだけ）

## 退けた案
- **場面ごとの復旧規則を残して整合させる**: 45〜50周で試して収束しなかった
- **state.json に「更新中」フラグを持つ**: log.md（追記専用・commit で改ざん耐性）の方が復旧の正本として信頼でき、状態ファイルの複製にもならない
- **書き込みを1ファイルに寄せてアトミックにする**: requirements.md（人間が読む）・state.json（機械が読む）・log.md（監査）の分離は D3 の設計判断。統合しない

## 再検討の条件
書き込みが冪等にできない項目が増えたとき（例: 外部サービスへの通知）。そのときは補償手順が要る。
