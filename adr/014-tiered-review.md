# ADR-014: レビューは変更の段階（A 軽微 / B 局所 / C 構造）で手順を変える

**状態**: Accepted（2026-09-06）／**Supersedes**: ADR-011 の「すべての変更に最大2周」の部分。周回の上限・合格条件・修正前の照合は ADR-011 を引き継ぐ

## 文脈
ADR-011 で周回を有界化しても、発火条件は「skills/ への**あらゆる変更**」のままで、1語の文面修正にもフル手順（回帰56件＋新規探索、約20分・25万トークン）が走っていた。2026-09-05〜06 の18周のうち、A/B 相当なら半分程度は省けた。回帰集は変更のたびに育つので、全件を毎回通すと周が伸び続ける。

## 決定
- 段階は `scripts/check-consistency.sh --tier` が `git diff` の対象ファイルと変更行の節見出しから**機械的に判定**する。人が判定を下げる（B→A）ときは理由を `plans/review-log.md` に書く
- **A**（skills/ に触れない、または文面のみ）: 機械チェックだけ。レビュー無し
- **B**（skills/ の局所変更）: 敵対的レビュー1周。回帰は**変更した領域タグ＋常時の GATE / RESUME** のみ、新規探索なし。直した領域の回帰だけ再確認して確定
- **C**（共通手順・経路表・05 最終受け入れ検証・reporting 書式・PM 区切り/受領規則・state.json・ADR の supersede）: フル手順（最大2周＋文面変更時の使う側＋ドライランは次の C とまとめて1回）
- 使う側レビューは「人間向け文面を変えたとき」だけ

## 理由
- レビューの価値は変更の相互作用の広さに比例する。局所変更に全件回帰を走らせても、動く可能性のある領域は限られる
- GATE と RESUME は「素通り・作業消失」のクラスなので、段階を問わず常に通す
- 機械判定にするのは「今回は軽微だから」という自己申告で C を B に落とす誘惑を防ぐため。下げる方向だけ人が決め、理由を残す

## 退けた案
- **全変更にフル手順**（ADR-011）: 上記のとおりコストが変更の大きさと無関係
- **段階を人が毎回判定する**: 判定が甘くなる。C の節に触ったかは機械で判定できる
- **回帰集を領域ごとに分割ファイルにする**: 1ファイルの方が全件通す C で読みやすい。絞り込みはタグで足りる

## 再検討の条件
B の1周で MAJOR が2回の変更で続けて出たとき（B の定義が広すぎる）。逆に C で2周目が3回連続ゼロのとき（C の手順を軽くしてよい）。
