# ADR-015: 優先度 must / should / could をタスク順の唯一の根拠にし、自律判断は次の報告で開示する

**状態**: Accepted（2026-09-06）

## 文脈
要件テンプレートには優先度列（must / should / could）があったが、付け方の定義が無く、仕様・設計・タスクのどこにも運ばれていなかった（死んだメタデータ）。実装順は「依存の少ない順」だけで、could の作り込みが must より先に走りうる。人間の要望は「最初は MVP に専念し、そこから作り込む。タスクは細かく切って優先度を付け、MVP に必要なものだけ先に作り、それ以外は低優先のタスクに回す。判断は安全なら AI が決め、あとから報告する」。

## 決定
- **優先度の意味は 02 が正**: must = 無いと成功基準を満たせない（must だけで MVP が成立）／should = 今回作るが後でよい／could = 余裕があれば。NR には付けない
- **03 が S-n の見出しに転記**する（複数 R-n なら最も高いもの。NR のみは must）。設計・タスク生成は requirements を読まないため、spec が運ぶ
- **05 Step 1 のタスク順は must 群 → should → could、群内は依存の少ない順**。must が should / could に依存するときは依存先を must 群に含めて並べ、理由を `decision` に記録する（凍結中の requirements.md は書き換えない）。バックログ整合・トリアージで後から挿入するタスクの位置（検証タスクの直前）は変えない
- **must 群の最後のタスク完了で中間報告**（MVP 到達の節目）
- **開発中間報告に「判断した点」行**（前回報告以降の `decision` を最大3件）。P1 に「安全側の判断は聞かずに決め、次の報告で開示する」を明記

## 理由
- 順序だけで「先頭の未完了を選ぶ」既存の選定規則が成立する。タスク行や state に優先度を複製すると正本が増える（アンチスコープ「状態ファイルの複製」）
- 人間は「後から修正を指示する」立場なので、判断は trail に埋めるだけでは足りず、報告に載って初めて修正の機会が生まれる

## 退けた案
- **タスク行に `／優先度:` を書く**: 台帳の書式変更が RESUME / TRIAGE の規則と回帰集に波及する。順序で足りる
- **could を「要件に書くが今回は作らない」にする**: 受け入れ検証・カバレッジ確認が全要件の合格を前提にしており、例外を作ると done 判定が崩れる。作らないものは非ゴール（P9 に明記）
- **最終報告にも判断一覧を載せる**: 最終報告は既に長い（使う側レビュー指摘）。trail が正で、中間報告で都度開示すれば足りる
- **優先度をヒアリングで人間に付けさせる**: 往復が増える。02 が推測で付け、ゲートの要約で must / should・could を分けて見せる方が P1 に沿う

## 再検討の条件
- ドライランで「must 群を終えた時点で起動できない」事例が出たら、must の定義（成功基準との対応）を見直す
- 「判断した点」が人間からノイズと言われたら、行を外して trail のみに戻す
