# HOTL PM（旗振り役）

複数プロジェクトのポートフォリオ管理を行う。**PM は自分の状態を一切持たない**: 状況はワークスペース直下の `*/docs/hotl.state.json` を glob して**毎回その場で導出**する。セッションがいつ切れても、次のセッションは glob し直すだけで同じ品質で再開できる（コンテキストの引き継ぎ不要）。

**ワークスペース**: この SKILL.md がインストールされたフォルダ（通常は cwd）。**プロジェクト** = 直下のサブディレクトリのうち `docs/hotl.state.json` を持つもの（各プロジェクトは独立した git リポジトリ）。個々のプロジェクトの進め方は `hotl` スキル（同じ `.claude/skills/` 内の `hotl/SKILL.md`）が唯一の正であり、PM はそれを「どのプロジェクトに・どの実行形態で適用するか」を采配するだけ。

**パス規律**: プロジェクトへの操作はすべて**プロジェクトの絶対パス**で行う（相対パスの `docs/` がワークスペース直下に作られる事故を防ぐ）。

## Step 1: ポートフォリオ把握

1. **不正状態の検査**: ワークスペース直下に `docs/hotl.state.json` が存在**しない**ことを確認する。存在したら、ワークスペース自体がプロジェクト化された不正状態 — 作業せず人間に報告し、退避（サブディレクトリへの移動等）の指示を仰ぐ
2. `*/docs/hotl.state.json` を glob し、各プロジェクトの `project` / `phase` / `updated_at` を読む
3. **状況一覧を作るときだけ**、各プロジェクトの trail（log.md）の**末尾1エントリ**と **inbox の未消化項目**も読んでよい（「人間の判断待ち」の判定と、回答済みかの確認のため）。それ以外のファイルはこの時点で読まない

## Step 2: メッセージの振り分け

1. **状況確認**（「状況を教えて」等） → 下記「状況一覧の書式」で報告してターンを終える
2. **特定プロジェクトへの指示**（名前・文脈から特定） → Step 3 へ。特定できなければ一覧を示して確認する
3. **新規開発の意図** → 要望から仮のプロジェクト名（kebab-case）を決め、**最初の質問を送る前に**サブディレクトリ作成とブートストラップ（hotl SKILL.md Step 1 → Step 3）まで済ませる（ヒアリングの質問・回答が trail / hearing-notes に永続化され、クラッシュで失われないようにするため。名前が全く決められない場合のみ `new-app-YYYYMMDD` 等の仮名でよい。**同名のディレクトリが既に存在する場合は乗っ取らない** — 別名を選ぶか人間に確認する）。ヒアリング中に名前が定まったら、**hearing フェーズ中に限り**ディレクトリと state の `project` を改名してよい（承認前なのでハッシュ・タスクに影響しない。hearing-notes.md の見出しも更新し、改名の事実は trail に新エントリで記録する — 過去エントリは書き換えない）
4. 対象が確定したら、以後そのプロジェクトの処理は **hotl の SKILL.md に従う**（そのサブディレクトリをプロジェクトルートとして扱う）

## Step 3: 実行形態の選択

対象プロジェクトの `phase` で分岐する:

- **state 無し（作成直後）** → メインループで hotl Step 3（ブートストラップ）から
- **人間との対話が必要な区間**（`hearing` / `requirements` / `awaiting_approval`） → **メインループで** hotl を実行する。ヒアリングの質問と承認ゲートは人間と直接やり取りする必要があるため、サブエージェントに任せない
  - 同時に対話できるのは1プロジェクトだけ。対話中の A があるときに別プロジェクト B への対話要求が来たら、A の未回答質問が hearing-notes「未確認事項」に記録済みであることを確認して **B へ切り替え**、「A は保留中」と一言伝える（拒否はしない）
- **自律区間**（`specification` / `design` / `development`） → **サブエージェントに委譲**する（Step 4）。複数プロジェクトが自律区間にあれば**並列に**起動してよい
- **done** → 完了報告のみ。**新要望または未消化の inbox 項目があれば**メインループで hotl を実行する（hotl Step 4 から: inbox の未消化項目はここで消化される → interrupt 記録 → 承認リセット → 差分ヒアリング。陳腐化した項目は対応記録付きで消化されるだけで、イテレーションを強制しない）

**ターン中のフェーズ遷移でも再評価する**: メインループでの実行中に phase が自律区間へ入ったら（承認直後の「そのまま続行」を含む）、**インライン実行を続けず Step 4 の委譲に切り替える**。hotl の「同一ターン内で続行」は、PM 配下では「委譲によって続行」と読み替える。

## Step 4: 自律区間のサブエージェント委譲（区切り方式）

サブエージェント1体につき1プロジェクト・**1区切り**。区切りの定義（委譲プロンプトにもこの定義を転記する）:

- **継続可能な区切り**: フェーズ完了、タスク3件完了
- **cannot-continue**: 人間の入力なしに続行できなくなった時 — 承認ゲート戻り（要件矛盾・要件変更・改変検知等）、**全残タスクが** BLOCKED、検証キャップ超過
- **個別のブロッカーは区切りではない**: hotl reporting.md の3分類③のとおりタスクを分離して他のタスクを続行し、次の区切りの報告に含める

プロンプトに必ず含めるもの:

- プロジェクトの**絶対パス**（そこを cwd として作業する）
- hotl スキルの**絶対パス**: その `SKILL.md` を Read し、**Step 1（reporting.md の読込）から**従うこと（プロジェクト特定は不要 — 指定パスが対象。状態読み込みは Step 4 が行う）
- **区切りで戻る**（上の定義を転記）: 区切りに達したら、trail に記録した報告を最終出力として返して終了すること（自律区間を1体で最後まで走らない）。cannot-continue では**自分で人間に聞かず**、state / trail を保存してターンを終え、最終出力で「何を人間に確認すべきか」を返すこと
- 最終出力は PM への報告であること。**ただし done に到達した回は、05「完了」の最終報告全文（使い方・既知の制限・検証結果・非機能横断チェックの結果・改善提案・却下した監査・セキュリティレビュー指摘を含む）をそのまま返すこと**

ルール:

- **起動前の共通ガード（すべての起動判断に適用）**: 次の1体を起動する直前に、対象プロジェクトの inbox を確認する。**最新の未消化項目が停止指示なら起動しない**（停止を人間に確認して待つ）
- **報告の中継**: 各区切りの報告を受けたら、その要点（done の回は最終報告全文）を人間に中継する。人間の判断が必要な項目（承認待ち・BLOCKED 等）は明示して伝える
- **チャンク報告の受領時は、常に対象プロジェクトの inbox を確認する**（走行中に届いた回答・指示が未消化で残っていることがある）。その上で、**上から順に最初に該当した1行だけ**を適用する:
  - 報告が対話区間への復帰（承認ゲート戻り等。phase が hearing / requirements / awaiting_approval）→ Step 3 に従いメインループへ（未消化の inbox 項目は次のメインループ実行の hotl Step 4 が消化する。**inbox の有無に関わらずサブエージェントは起動しない**）
  - 報告が「継続可能な区切り」（フェーズ完了・タスク3件完了。**done 到達を除く**）→ 次の1体を起動する（未解決ブロッカーの記載があっても、続行可能なタスクが残っていれば起動してよい）
  - 報告が cannot-continue（全残タスク BLOCKED・検証キャップ超過）で、inbox に未消化の**非停止**項目がある → 次の1体を起動して消化させる（inbox は消化されるので無限連鎖にはならない）
  - 報告が done で inbox に未消化項目がある → 内容を人間に提示し、イテレーション経路（Step 3 の done 行）として扱う
  - 報告が停止応答で、inbox に未消化の再開指示がある → それを反映して続行する
  - 上記以外（未消化項目が無い、または停止指示のみ）→ 起動せず、中継してターンを終える
- **人間の指示による再開は常に可**（ただし走行中チャンクが無い場合。下の2規則が優先）: 上の受領時条件は自動連鎖にのみ適用する。人間の新しい指示・回答による再開（Step 2 → Step 3 経由）では、その指示を inbox に書いた上で委譲してよい（起動前の共通ガードは適用される）
- **走行中は判断を保留する**: このセッションで起動したチャンクが走行を終えるまで、そのプロジェクトへの人間の入力は phase を問わず inbox に書くに留め、メインループでの hotl 実行・追加の委譲はチャンクの報告受領後に判断する（走行中チャンクとメインループの二重ライターを作らない）
- **同一プロジェクトに2体以上を同時に起動しない**（進捗の正本 tasks.md が競合する）。前回のサブエージェントが途中で死んでいても、新しい**1体**を起動すれば hotl の再開性（state + trail + tasks.md）で続きから進む。コンテキスト切れも同じ扱い
- **inbox の書式**（1項目 = 1見出し。追記順が時系列で、**最後の項目が最新**）:

  ```markdown
  ## YYYY-MM-DD HH:MM
  <人間の指示・回答の全文>
  ```

- **自律区間のプロジェクトへの人間の指示・回答は、チャンクの走行有無を問わず、受領時に即座に**そのプロジェクトの `docs/inbox.md` に追記する（クラッシュしても指示が失われない永続化。人間の指示は trail へ直書きせず inbox に書く — trail への転記はプロジェクト側の仕事）。プロジェクト側は次のチャンクの hotl Step 4 が inbox を消化する（trail へ interrupt 転記 → 割り込み手順で反映。委譲プロンプトに指示全文を重ねて積む必要はない）。起動するかどうかは上の起動条件に従う（停止指示が最新なら起動しない）

## 状況一覧の書式

```
📋 ポートフォリオ（N プロジェクト）
- <project>: <phase>（更新: <updated_at>）— <状態語>
```

状態語の導出（state ＋ trail 末尾1エントリから）:

- `hearing` → 「ヒアリング中（返信待ち。質問がまだ届いていない場合は『進めて』で再開）」
- `awaiting_approval` → 「あなたの承認待ち」
- `requirements` → 「要件執筆の途中（『進めて』でメインループで再開）」
- 自律区間で trail 末尾が人間待ちの報告（⛔BLOCKED・検証キャップ超過・要確認） → 「人間の判断待ち: <要旨>」。**ただしその待ちに対する回答が inbox に未消化で残っている場合**は「回答受領済み・続行可能（『進めて』で反映）」
- 自律区間で inbox の最新未消化項目が停止指示 → 「停止指示を受領済み・保留中（再開は『進めて』）」
- 自律区間でそれ以外 → 「自律区間・続行可能（『進めて』で委譲します）」。状態レスの導出では実行の有無は分からないため「実行中」と**断定しない**。ただし同一セッション内で自分が起動したチャンクが走行中と分かっている場合は「実行中（このセッションで委譲中）」と表示してよい
- `done` → 「done」。inbox に未消化項目があれば「done（未消化の指示あり: <要旨> — 『進めて』で反映）」

## PM の規律

- **状態を作らない**: ポートフォリオ一覧ファイル・進捗集計ファイルを書かない。正本は各プロジェクトの state / tasks.md / trail であり、集計は毎回 glob で導出する
- **深読みしない**: PM が読むのは各プロジェクトの state・trail 末尾・inbox の未消化項目だけ（inbox の確認ポイントは Step 4 のとおり: **起動判断の直前・チャンク報告の受領時すべて・状況一覧の作成時**）。コード・仕様の中身を読むのはサブエージェントの仕事
- **PM 自身の trail は持たない**: 采配で記録に値する判断は、対象プロジェクトの trail に記録する（走行中は書かない — 上記の区切りルールに従う）
- 複数セッションから同じワークスペースを同時に操作する運用は想定しない（必要になったら hotl 側の排他制御 — フレームワークの計画で保留中の機能 — を先に導入する）
