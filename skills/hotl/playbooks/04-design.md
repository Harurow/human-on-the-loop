# Phase: 設計（自律区間）

**入力**: `docs/spec.md`
**成果物**: `docs/design.md`（スキルの `templates/design.md` に従う）

## 実行形態（コンテキスト分離）

サブエージェントが使える場合、**fresh context のサブエージェント1体**に以下だけを渡して `docs/design.md` を書かせる。会話履歴は渡さない:

- `docs/spec.md` 全文
- スキルの `templates/design.md`（書式）
- この playbook の「進め方」「自己検証」「判断に迷ったら（執筆時の原則）」節
- **差分更新・書きかけ再開の場合はさらに**: 既存の `docs/design.md` と、変更点の要約（変更された S-n とその内容）

サブエージェントが使えない場合は、同じ入力制約を意識してインラインで実行する。
**いずれの場合も**、完成後にメインループが仕様カバレッジ（S-n の割り当て漏れ）を検算する（サブエージェントの出力こそ検算対象）。検算で漏れがあれば指摘を添えて同じ入力で1回再実行し、なお残ればメインループがインラインで修正して trail に記録する。

## 進め方

1. `docs/design.md` が**既に存在する場合**（イテレーション・再開）は再生成せず差分更新にする: 追加・変更された仕様 (S-n) に関わるモジュール・データ設計を追加・修正し、**削除された仕様に対応する記述は削除する**。初回のみテンプレートをコピーして雛形にする。既存ファイルにガイドコメントや未記入の `<...>` が残っていれば前回の書きかけなので、差分更新ではなく未完成部分を埋めて完成させる
2. **技術選定**: 言語・フレームワーク・データ保存を選ぶ。判断基準:
   - spec の「前提・制約」（実行環境・既存資産・外部サービス）を満たす範囲で選ぶ
   - 運用者は個人。運用コスト最小・依存最小を優先する
   - 各言語・領域のデファクトスタンダードを選ぶ（凝った選択をしない）
   - 理由と検討した代替案を必ず書く
3. **アーキテクチャ**: 全体構成をテキスト図で描く
4. **モジュール分割**: 各モジュールの責務と、担当する仕様 ID (S-n) を表にする
5. **データ設計**: スキーマ・ファイルフォーマットを確定する
6. **テスト戦略**: 何を unit / integration / e2e のどのレベルで検証するか。テストランナーの選択
7. **検証ツールチェーン**: テンプレートの表に従い、カテゴリ（formatter / linter / 型検査 / テスト / ビルド / セキュリティ・依存検査）ごとに導入可否とツールを決める（機械で検査できるものを AI の目視で代替しない）。セットアップは開発の最初のタスク（環境構築）に含まれるよう明記する。**formatter / linter の対象から `docs/` を除外する**（承認済み requirements.md を機械が書き換えると SKILL.md Step 4 のハッシュ照合で承認リセットになる）

**文書の深さはプロジェクト規模に比例させる**: 小規模ならモジュール表と技術選定が本体で、図は数行でよい。

## 判断に迷ったら（執筆時の原則）

仕様の範囲内で最も単純な設計を選び、その判断を design 内に記録する。**人間には聞かない**（自律区間）。
**仕様同士の矛盾を見つけた場合は、設計を止めて矛盾の指摘を返す**（自分で仕様や state を修正しない）。

## 仕様矛盾への対応（メインループ）

矛盾の指摘を受けたら、メインループが spec.md を差分修正し（03 の執筆時原則に従い、承認済み要件の範囲内で）、判断を trail に記録して設計を続行する。**要件自体の矛盾に帰着する場合**は 03「要件矛盾への対応」に従い承認リセットする。

## 自己検証

spec.md のすべての仕様項目 (S-n) がモジュール構成表のどこかに割り当てられていること、技術選定・構成が spec の「前提・制約」に反していないことを確認する。
逆方向も確認する: **spec.md に存在しない仕様を参照する記述（削除された S-n の残骸）が無い**こと。
未割り当て・残骸があれば修正してから完了する。

## 完了

SKILL.md Step 6 を実行（次 phase: `development`）。
