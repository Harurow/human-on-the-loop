# Phase: 設計（自律区間）

**入力**: `docs/spec.md`
**成果物**: `docs/design.md`（スキルの `templates/design.md` に従う）

## 実行形態（コンテキスト分離）

サブエージェントが使える場合、**fresh context のサブエージェント1体**に以下だけを渡して `docs/design.md` を書かせる。会話履歴は渡さない:

- `docs/spec.md` 全文
- スキルの `templates/design.md`（書式）
- この playbook の「進め方」「自己検証」節
- **差分更新の場合はさらに**: 既存の `docs/design.md` と、変更点の要約（変更された S-n とその内容）

サブエージェントが使えない場合は、同じ入力制約を意識してインラインで実行する。
**いずれの場合も**、完成後にメインループが仕様カバレッジ（S-n の割り当て漏れ）を検算する（サブエージェントの出力こそ検算対象）。

## 進め方

1. `docs/design.md` が**既に存在する場合**（イテレーション・再開）は再生成せず差分更新にする: 追加・変更された仕様 (S-n) に関わるモジュール・データ設計を追加・修正し、**削除された仕様に対応する記述は削除する**。初回のみテンプレートをコピーして雛形にする（`<!-- ... -->` のガイドコメントは削除して記入する）
2. **技術選定**: 言語・フレームワーク・データ保存を選ぶ。判断基準:
   - 運用者は個人。運用コスト最小・依存最小を優先する
   - 各言語・領域のデファクトスタンダードを選ぶ（凝った選択をしない）
   - 理由と検討した代替案を必ず書く
3. **アーキテクチャ**: 全体構成をテキスト図で描く
4. **モジュール分割**: 各モジュールの責務と、担当する仕様 ID (S-n) を表にする
5. **データ設計**: スキーマ・ファイルフォーマットを確定する
6. **テスト戦略**: 何を unit / integration / e2e のどのレベルで検証するか。テストランナーの選択

**文書の深さはプロジェクト規模に比例させる**: 小規模ならモジュール表と技術選定が本体で、図は数行でよい。

## 自己検証

spec.md のすべての仕様項目 (S-n) がモジュール構成表のどこかに割り当てられていることを確認する。
逆方向も確認する: **spec.md に存在しない仕様を参照する記述（削除された S-n の残骸）が無い**こと。
未割り当て・残骸があれば修正してから完了する。

## 完了

SKILL.md Step 6 を実行（次 phase: `development`）し、**同一ターン内で** `05-development.md` を Read して続行する。
