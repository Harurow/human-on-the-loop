# Phase: ヒアリング

**ゴール**: ユーザーが「本当に欲しいもの」を言語化する。言われたものをそのまま作るのではなく、背後の課題を掘り当てる。
**成果物**: `docs/hearing-notes.md`（会話のたびに更新する構造化メモ）

## 進め方

- 1回のメッセージで質問は**最大3つ**。尋問にしない
- オープンクエスチョンから始め、答えを受けて深掘りする
- 質問を送ったらターンを終了して返信を待つ（このフェーズだけは人間のテンポに合わせる）
- 毎回、返信の内容を `docs/hearing-notes.md` に反映してから次の質問を組み立てる

## 技法

使えるものを状況に応じて。全部やる必要はない:

- **5-whys**: 「なぜそれが欲しいのか」を掘る。表面の機能要望の下にある動機に到達する
- **具体シナリオの再現**: 「最近それが欲しかった瞬間を教えてください。何をしていて、何に困りましたか」— 抽象論より実話
- **ユーザーストーリー**: 誰が・いつ・何のために使うのかを埋める
- **MVP スコープ交渉**: 「最初の1週間、毎日使う機能だけに絞るとどれですか」— 全部盛りを防ぐ
- **非ゴールの明示的確認**: 「逆に、今回は無くていいものは何ですか」— 後のスコープクリープ防止
- **成功基準の引き出し**: 「1ヶ月後、これが成功だったと思える状態は？」

## hearing-notes.md の構造

```markdown
# ヒアリングノート: <app-name>

## ユーザー像・利用シーン
## コア課題（なぜ欲しいのか）
## 欲しい機能（ユーザーの言葉のまま）
## MVP スコープ（合意済み）
## 非ゴール（合意済み）
## 成功基準
## 未確認事項
```

## 終了条件

以下がすべて埋まったら終了できる:

- [ ] ユーザー像・利用シーンが具体的である
- [ ] コア課題（機能要望ではなく、解決したい問題）が言語化されている
- [ ] MVP 機能が列挙され、ユーザーと合意している
- [ ] 非ゴールが明示されている
- [ ] 成功基準がある

終了時: ヒアリング結果の要約を提示し、「要件定義に進みます」と宣言して `phase` を `requirements` へ遷移（SKILL.md Step 6）。
**要件定義は同一ターン内で続行してよい**（次の返信待ちは承認ゲート）。
