# Phase: ヒアリング

**ゴール**: ユーザーが「本当に欲しいもの」を言語化する。言われたものをそのまま作るのではなく、背後の課題を掘り当てる。
**成果物**: `docs/hearing-notes.md`（会話のたびに更新する構造化メモ）

## 進め方（propose-and-confirm 方式）

往復を最小にする。空欄を1問ずつ潰すのではなく、**推測ドラフトを提示して一括訂正を求める**:

1. **1往復目**: ユーザーの最初の要望から不明な核心（コア課題・利用シーン）を最大3問で聞く。同時に、わかる範囲で hearing-notes.md を作り始める
2. **2往復目以降**: 回答を得たら、hearing-notes の**全節を推測込みで埋めたドラフト全文**を提示し、「違うところを指摘してください」と一括訂正を求める。推測で埋めた箇所は「（推測）」と明記する。**最初のドラフト提示にはコンセプト提案（下記。初回、または形の見直しを伴うイテレーション時）を含める**
3. ユーザーの訂正が無くなり、終了条件を満たしたら終了

- 1回のメッセージで質問は最大3つ。尋問にしない
- 質問を送ったらターンを終了して返信を待つ（このフェーズだけは人間のテンポに合わせる）
- **ターン終了前に必ず**: 返信内容を hearing-notes.md に反映し、送信済みで未回答の質問を「未確認事項」節に記録する（セッションが切れても次のエージェントが文脈を引き継げるように）

## 深掘りの技法

ドラフトの精度を上げるために状況に応じて使う。全部やる必要はない:

- **5-whys**: 「なぜそれが欲しいのか」を掘る。表面の機能要望の下にある動機に到達する
- **具体シナリオの再現**: 「最近それが欲しかった瞬間を教えてください。何をしていて、何に困りましたか」— 抽象論より実話
- **ユーザーストーリー**: 誰が・いつ・何のために使うのかを埋める
- **MVP スコープ交渉**: 「最初の1週間、毎日使う機能だけに絞るとどれですか」— 全部盛りを防ぐ
- **非ゴールの明示的確認**: 「逆に、今回は無くていいものは何ですか」— 後のスコープクリープ防止
- **成功基準の引き出し**: 「1ヶ月後、これが成功だったと思える状態は？」

## 非機能の3観点（ドラフトに必ず含める）

性能目標・費用上限（想定実行頻度を含む）・公開範囲/データの機微度の3点は、上の技法とは別に**推測ドラフトの「非機能」節に必ず埋めて提示**する（例: 「1回の処理は5分以内」「外部 API は月 $30 まで（1日6回実行の想定）」「家庭内 LAN のみ・投資メモ相当」）。ユーザーが訂正しなければ要件定義でその値を「提案」由来として採用する（要件定義フェーズで改めて質問しない）。終了条件には含めない（未確定でも 02 の既定値経路で埋まる）。

## コンセプト提案（こんなアプリはどうですか）

御用聞きではなく**コンサルタント**として振る舞う。コア課題が見えたら（通常1往復目の回答後）、**アプリの形そのものを2〜3案提案する**。ユーザーの言った形をなぞるだけでなく、**期待の一段・二段上をいく案を必ず1つは含める**（課題の捉え直し・自動化・データ活用など、頼まれていないが価値が跳ね上がる方向）:

- 各案は「名前・形態（CLI / Web / bot 等）・コア機能・向き不向き」を2〜3行で提示する
- 案の切り口の例: **ミニマム案**（最短で動く）／**自動化寄り案**（手間を減らす）／**別アングル案**（課題の捉え直し・期待超え）
- **propose-and-confirm の最初のドラフトに含めて提示する**（別メッセージに分けて往復を増やさない。採用・混合の希望を一括で聞く）
- 選ばれた案（混合を含む）を hearing-notes の「エージェント提案」節に記録し、**MVP スコープは選ばれたコンセプトに基づいて**合意する
- **採用したコンセプトで不要になったユーザー発の要望**は、hearing-notes の「非ゴール」節へ理由付きで移し、置き換えの判断を log.md に記録する（これを怠ると要件定義の漏れチェックで復活する）
- **イテレーション（差分ヒアリング）では採用済みコンセプトを蒸し返さない**: コンセプト提案を行うのは初回、または要望がアプリの形の見直しを含む場合のみ

## 機能提案（ニーズを超える価値）

要求をそのまま形にするだけでは足りない。**要求と「真に欲しいもの」は往々にして異なり、ユーザーが言語化していない価値がある**。コンセプトが定まったら、その中の改善も能動的に提案する:

- 隣接する困りごとの解消・手作業の自動化・より良い体験など、**1〜3件に絞って**具体的に提示する
- 提案は「提案」と明示し、**採否は必ずユーザーが決める**（勝手にスコープへ入れない）
- 採否を hearing-notes の「エージェント提案」節に記録する。採用された提案は要件に出所「提案」として反映される

## hearing-notes.md の構造

```markdown
# ヒアリングノート: <app-name>

## ユーザー像・利用シーン
## コア課題（なぜ欲しいのか）
## 欲しい機能（ユーザーの言葉のまま）
## エージェント提案（採否付き）
## MVP スコープ（合意済み）
## 非ゴール（合意済み）
## 成功基準
## 非機能（性能・費用と想定実行頻度・公開範囲）
## 未確認事項
```

## 終了条件

以下がすべて埋まったら（推測ではなくユーザーの確認済みで）終了できる:

- [ ] コンセプトの採否が確定している（初回、または形の見直しを伴うイテレーション時）
- [ ] ユーザー像・利用シーンが具体的である
- [ ] コア課題（機能要望ではなく、解決したい問題）が言語化されている
- [ ] MVP 機能が列挙され、ユーザーと合意している
- [ ] 非ゴールが明示されている
- [ ] 成功基準がある

終了時: 「要件定義に進みます」と宣言し、SKILL.md Step 6 を実行（次 phase: requirements）。
**要件定義は同一ターン内でそのまま続行する**（ここでターンを終えない。次の返信待ちは承認ゲート）。

## イテレーション時（差分ヒアリング）

既存の hearing-notes.md がある場合は再生成せず、新しい要望を各節に追記・修正する。変更が小さければ1往復（ドラフト提示→確認）で終えてよい。
