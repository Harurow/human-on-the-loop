# Phase: 仕様化（自律区間）

**入力**: `docs/requirements.md`（承認済み）
**成果物**: `docs/spec.md`（スキルの `templates/spec.md` に従う）

## 実行形態（コンテキスト分離）

サブエージェントが使える場合、**fresh context のサブエージェント1体**に以下だけを渡して `docs/spec.md` を書かせる。会話履歴・ヒアリングの経緯は渡さない:

- `docs/requirements.md` 全文
- スキルの `templates/spec.md`（書式）
- この playbook の「進め方」「トレーサビリティ」「判断に迷ったら（執筆時の原則）」節
- 出力先の**絶対パス**（`docs/spec.md`）と、そこを cwd として作業すること
- **差分更新・書きかけ再開の場合はさらに**: 既存の `docs/spec.md` と、変更点の要約（変更された R-n とその内容。メインループが log.md・会話から把握しているもの）

サブエージェントが使えない場合は、同じ入力制約を意識してインラインで実行する。
**いずれの場合も**、完成後にメインループがトレーサビリティ表を検算する（サブエージェントの出力こそ検算対象）。検算で漏れがあれば、**指摘の要約と既存の `docs/spec.md` を差分更新の入力として渡して**1回再実行し（新しいサブエージェント1体。テンプレートからの再生成をさせない）、なお残ればメインループがインラインで修正して trail に記録する。

## 進め方

1. テンプレートをコピーして書くときは、**`<!-- -->` のガイドコメントをすべて削除し、`<...>` の記入欄をすべて埋める**（**どちらかが残っていれば「書きかけ」**と判定される。成果物本文に `<file>` のようなプレースホルダを正当に書く場合は、コード引用〔バッククォート〕の中に入れて記入欄と区別する）。**既存の ID は永続で、削除しても欠番のまま残し、番号を振り直さない**（詰め直すと下流のタスクの「関連」がずれ、実装済みの機能が「削除された仕様」と誤判定されて除去タスクが生まれる）。`docs/spec.md` が**既に存在する場合**（イテレーション・再開）は再生成せず差分更新にする: 追加・変更された要件 (R-n) に対応する仕様項目 (S-n) を追加・修正し、**削除された要件に対応する仕様項目は削除する**。初回のみテンプレートをコピーして雛形にする。既存ファイルにガイドコメントや未記入の `<...>` が残っていれば前回の書きかけなので、差分更新ではなく未完成部分を埋めて完成させる
2. requirements の「前提・制約」を spec の同名節に転記する（設計サブエージェントは requirements を読まないため、ここで運ぶ）
3. 各要件 (R-n) を振る舞い仕様 (S-n) に展開する:
   - **入力・出力・エラー時挙動**を必ず明記する
   - 1要件が複数の仕様項目になるのは普通。逆に対応要件のない仕様項目は書かない（スコープクリープ）
   - 見出しに対応要件の**優先度を転記**する（`（対応: R-1 ／優先度: must）`。複数の R-n に対応するなら最も高いもの。NR のみに対応する S-n は must）。下流（設計・タスク生成）は requirements を読まないので、ここで運ぶ
   - **非機能要件 (NR-n) も対象**: 該当する S-n に制約として付記するか、専用の仕様項目を立てる。トレーサビリティ表には R-n と NR-n の両方を含める
4. 外形を定義する: CLI ならコマンド体系と出力例、Web なら画面一覧と遷移、API ならエンドポイント
5. データモデル素案を書く（詳細な設計は次フェーズ。ここでは保存すべき情報の構造まで）

**文書の深さはプロジェクト規模に比例させる**: 機能要件5件以下の小規模なら S-n は R-n と1対1で簡潔に書けばよい。厚い文書自体に価値はない。

## トレーサビリティ

要件トレーサビリティ表を埋め、**対応する仕様のない要件がゼロ**であることを確認する（「なし（理由）」と書かれた非機能要件は表で「該当なし」と記し、このゼロ確認の対象外とする）。
逆方向も確認する: **対応する要件のない仕様項目 (S-n) がゼロ**であること（削除された要件の残骸を残さない）。
漏れ・残骸があれば修正してから完了する。

## 判断に迷ったら（執筆時の原則）

承認済み要件の範囲内で最も単純な解釈を選び、その判断を spec 内に記録する。**人間には聞かない**（自律区間）。
**要件自体の矛盾を見つけた場合は、仕様化を止めて矛盾の指摘を返す**（自分で要件や state を修正しない）。

## 要件矛盾への対応（メインループ）

矛盾の指摘を受けたら、**まず指摘の全文と修正案を `finding` として trail に記録し**（委譲実行モードでは報告が1〜2行に縮むため、記録しないと 02 を実行する側が矛盾の内容を復元できない）、**承認リセットで凍結が解けてから要件に反映し、その時点でその finding に対応記録「修正済み」を追記する**（凍結中〔`approved` が true〕の requirements.md を先に書き換えると、改変検知として二重に報告される。未対応のまま残すと 05 の初回タスク化と整合性監査が開発タスクとして拾う）、SKILL.md の**承認リセット**（次 phase: `requirements`）を行い、矛盾点の説明と修正案を添えて承認ゲートを再実行する。

## 完了

SKILL.md Step 6 を実行（次 phase: `design`）。
