# 報告プロトコル

human-on-the-loop の原則: 人間は「ループの上」にいる。報告は**非ブロッキング**であり、返信を待たない。
人間の返信を待ってよいのは原則、ヒアリング中の質問と要件承認ゲートの2箇所だけ（例外を含む完全なターン終了規則は SKILL.md Step 6 を正とする）。

## 届け方

- **途中報告**: 通常のテキスト出力（実行は止めない）
- **最終報告**: ターン終了時の最終メッセージ
- **ヒアリング質問**: 質問して返信を待つ。選択式にできる場合は AskUserQuestion も可
- **承認ゲート**: AskUserQuestion（承認 / 修正依頼 / 質問）

## 人間向け文面の共通規則

- **用語**: 内部用語（phase・state・trail・interrupt・S-n・ハッシュ・委譲・不変条件等）を人間向け文面に出さない（**例外: タスク ID `T-n` は、どの作業かを指すためタスク名を添えれば書いてよい** — 例「T-4（天気 API の取得）」）。フェーズ名は次のラベルで書く: hearing=ヒアリング / requirements=要件定義 / awaiting_approval=承認待ち / specification=仕様化 / design=設計 / development=開発 / done=完了。時刻は「今日 09:12」程度に丸める
- **次の行動**: 人間の返事や作業が要る報告には「お願い:」行で、取れる行動を選択肢として具体的に書く。要らなければ「あなたの作業はありません」と書く（フェーズ完了・開発中間報告の書式には付けない。承認ゲートの AskUserQuestion が「お願い」を兼ねる）
- **収束しなかった指摘の開示の型**（02 の3周超過・監査の2周超過・UX の3周超過に共通）: 専門用語で列挙せず、**(1) 何を検査していたか（1行・平たく）、(2) 何周やって何が残ったか（件数と傾向。例「細かい詰めどころが最後まで出続けた」）、(3) 指摘を反映したのか未反映なのか、(4) 人間に判断してほしいことがあるか（無ければ「ありません」）**の4点で書く。個々の指摘を人間向け文面に転記しない（詳細は trail と成果物にある）。
- **選択で答えられることは選択式で聞く**: **返信を待ってターンを終了する場面**（SKILL.md Step 6 のターン終了許可リストのうち、承認ゲートの承認/修正/質問、「承認と受け取ってよいですか」の再確認、⚠️ キャップ超過の A/B/C/D、環境の確認とプロジェクト特定の確認〔Step 2 の新規確認・不正状態の退避・対象プロジェクト／Step 3 の docs 衝突・入れ子リポジトリ〕、**選択肢の形にできるヒアリング質問**）に限り、文章で書かせず **AskUserQuestion（選択式）**で提示する。**非ブロッキングの報告（BLOCKED の選択肢・改善提案・中間報告・最終報告）は選択式にしない** — 返信を待たずに他のタスクを続行するため（P1）。自由記述が必要な選択肢（修正内容・ヒント等）は、選択肢の説明にその旨を書き、**「その他」で自由に書けること**を添える。報告本文（要約・理由・お願い行）は従来どおりテキストで出し、**選択式はその直後の1問**にする（本文を選択肢に詰め込まない）。**選択式が使えない環境**（サブエージェント実行中・非対話）では同じ選択肢をテキストで提示する — 判定規則は提示方法によらず同じ
- **宛名**: hotl-pm の委譲プロンプトで起動された場合、または Step 2 のワークスペースガード経由でプロジェクトを特定した場合は、人間に届く報告・質問の先頭に `[<project>]` を付ける（PM の中継時は PM が「付いていなければ付ける」）
- **秘密情報**: 人間のメッセージに API キー等の値が含まれていたら、trail・inbox には伏せ字で転記し、値は `.env` 等へ移すよう案内する（本人が置けなければ代わりに置いてよい。値そのものは docs/ に残さない）。**ヒアリングで聞いた生活・業務の情報は docs/ に残り git 履歴にも入る**ので、最終報告に1行で開示する（「このリポジトリを他の人に見せる場合、docs/ にヒアリングの内容が入っている点にご注意ください」）

## 再開時の一言

自律区間のプロジェクトを「続きから」等で再開したとき、SKILL.md Step 4 の検査と inbox 消化を終えて playbook に入る直前に、1〜2行で「前回どこまで（例: T-5 まで完了、停止指示で中断）／今から何を／あなたの作業はありません」を出す。状況確認クエリと委譲実行モード（人間に届かない）では出さない。

## AgentTrail（docs/log.md）

log.md は単なるログではなく **AgentTrail** — エージェントの全判断・行動を後から監査・再構成できる**追記専用の証跡**である。目的は2つ:

1. コンテキストが切り替わっても、新しいエージェントが state + trail だけで同じ品質で再開できる（SKILL.md Step 4 の文脈復元はこれを正とする）
2. 人間が後から「なぜそうなったか」を監査できる

ルール:

- **追記専用**: 過去のエントリを書き換え・削除しない。訂正は新しいエントリで行う
- すべての報告は、送信と同時に同内容を trail に追記する
- 報告以外にも、意思決定・レビュー指摘・承認・割り込み・提案が発生した時点で追記する
- **対応の記録**: finding / interrupt は、対応した時点で結果（修正済み / ②でタスク化 / ③で分離 / 最終報告で開示〔非機能横断チェックの MINOR、収束キャップ超過で開示に回した指摘、凍結中の要件への指摘〕 / ゲートで開示〔02 の残指摘〕 / 却下＋根拠 / 再開 / 回答として処理 / イテレーション開始 / 後続指示により陳腐化〔後続のゲート提示で無効になった承認的発言を含む〕 / 質問に回答済み / T-n として登録 / 再確認中〔暫定。**承認かどうかを聞き返している**状態。確定時に新エントリ〕 / 本文待ち〔暫定。**修正内容・質問・ヒントの本文を待っている**状態。届いたら新エントリ。**本文とみなすのは内容のあるメッセージだけ** — 再開語（「続きから」「進めて」）は本文ではなく、同じ依頼文を再提示して待ち続ける。停止・状況確認は下の割り込み手順で処理する〕 / 停止済み / 反映済み〔方針変更〕 / 入力確認済み〔人間待ちへの回答〕）を**新しいエントリ**（type は却下なら `decision`、それ以外は `report`。`関連:` に元エントリの見出し）で追記する（同じエントリ内に書いた「（対応: …）」は対応記録ではない）。**`関連:` には元エントリの見出しを逐語で引用する**（時刻＋`[type]`＋タイトル。複数まとめるときは1行に読点区切りで**全部を逐語で**並べる。「上記2件」のような省略は、整合性監査の未処理判定が見出し一致で行われるため未処理と誤判定される）。書式:

```
## YYYY-MM-DD HH:MM [report|decision] <元のタイトル> の対応
関連: <元エントリの見出しを逐語で>
対応: <上の語彙から1つ>
```

（`decision` は「却下＋根拠」のときだけ。それ以外は `report`）。対応エントリの無い finding / interrupt が「未処理」である（整合性監査の判定基準）。proposal は done の最終報告まで pending が正常
- **秘密情報の値を trail に書かない**（trail は commit される）。接続情報・キー・トークンは名前と置き場所（.env 等）の参照のみ記す
- フェーズ遷移の commit に必ず含める（git 履歴が改ざん耐性を与える）

エントリ書式（時刻は `date +"%Y-%m-%d %H:%M"` の実行結果）:

```markdown
## YYYY-MM-DD HH:MM [type] <タイトル>
<what: 何をした・何を決めたか>
理由: <why: 根拠。自明なら省略可>
関連: <ファイル・commit・指摘元。無ければ省略>
```

type の分類:

| type | 用途 |
|---|---|
| report | フェーズ完了・中間報告（送信した報告と同内容）、開始・完了・周の着手などの節目、タスク完了の証拠（実行結果・テスト出力の要旨）、却下以外の対応記録 |
| decision | 技術選定・仕様解釈・WIP 引き継ぎ判断などの意思決定 |
| finding | レビュー指摘・矛盾・受け入れ検証の結果 |
| approval | 承認・承認リセット |
| interrupt | 人間からの入力（割り込み・方針変更・停止・修正依頼） |
| proposal | ユーザーの要求を超える改善提案（採否も追記） |

## フェーズ完了報告の書式（前進遷移のみ）

3〜6行で簡潔に:

```
✅ <フェーズ名> 完了
主要な決定: <最大3点、箇条書き>
成果物: <ファイルパス>
次: <次フェーズ名>（自律区間の場合は「このまま続行します」。委譲実行モードでは区切りで戻るため「このあと続けます」とし、PM が中継する）
```

**例外 — development → done の最終報告**: この書式ではなく 05「完了」が定める全項目で報告する。行数制限は適用しない（ただし簡潔に）。
**例外 — requirements → awaiting_approval**: 02 の承認ゲート提示（要約10行以内＋非機能・前提の平たい各行＋AskUserQuestion）が報告書式を兼ねる。

## フェーズ後退報告の書式（承認リセット・差し戻し）

```
⏪ <旧フェーズ> → <新フェーズ>（理由: 要件の変更 / 要件の矛盾 / 要件定義書が承認後に変わっていた / 修正依頼 / 次の改良 / 不具合の修正 / 内部状態の不整合）
<何が起きたか、1〜2行。開発中からの後退なら「これまでの実装は引き継ぎます」を添える>
次: <こちらで要件定義書を直し、再度承認をお願いします / 追加分のヒアリングをします / 修正して再検証します（承認は不要です） 等>
お願い: <人間がすること。無ければ「あなたの作業はありません」。同一ターンでゲート再提示・差分ヒアリングの質問まで進む場合は省く。委譲実行モードではチャンクは書き、PM が続けてゲートを出すなら中継時に落とす>
```

## 開発中間報告の書式

tasks.md 生成直後は「🔨 開発開始: 全 N タスク」の1行。以後は次のとおり:

タスク3件完了（`[x]` のみ数える。`[-]` は含めない）ごと、またはブロッカー発生時:

```
🔨 開発中: <完了タスク数>/<総タスク数>
直近の完了: <T-n タスク名（最大3件）>
ブロッカー: <未解決の BLOCKED タスクを毎回再掲。なければ省略>
```

## 成果物を見せるときの改善提案

対象: **アプリ自体の成果物**（エンドユーザー向けの画面・出力ファイル・生成物）を初めてユーザーに提示するとき、および見た目・構成が大きく変わる更新を提示するとき。docs/ の中間ドキュメント（要件・仕様・設計）は対象外（それらの提案経路は PRINCIPLES P2 と 02 の承認ゲート）。「初めて」の判定は trail を正とする: その成果物についての本節の proposal（または「提案なし」記録）が無ければ初提示。

手順:

1. 提示前に「ユーザーがこれを実際に使う場面」を具体的にシミュレーションする（毎日どう眺めるか・何をクリックするか・何を比較するか）
2. そこから出る改善案を**原則2〜5件**、優先度と工数感（小/中/大）付きで列挙する。実質的な改善が出なければ捻出せず「提案なし（使用シミュレーション済み）」と報告本文に明記してよい（P7 Lean。提案のノルマ化はしない。この場合 proposal type にはせず、報告の trail 追記が判定の記録を兼ねる）
3. 提案は**提示と同時に** trail へ proposal として記録する（どの成果物への提案かを「関連:」に明記。採否が判明したら追記。done まで pending は正常）
4. 採否はユーザーに委ねるが**返信は待たず続行**する（非ブロッキング。採否は割り込みか最終報告で回収）。提案ブロックの末尾に伝え方を1行添える: 「採用したい提案は番号でどうぞ（短い確認のあと要件に反映し、再度承認をお願いする流れになります）。不要なら返信は要りません」

提案ブロックは報告本文とは別立てで添え、各報告書式の行数制限には**含めない**。done の最終報告での改善提案の扱いは 05「完了」がこの節を参照する（正本はこの節）。

根拠: PRINCIPLES P2（コンサルタント責務 —「期待の一段・二段上をいく案を必ず含める」）。指摘されてから直すのは期待未満。

## 介入の案内

自律区間の**開始時（承認直後の報告）に1回だけ**、次の一行を添える。以後の報告には毎回付けない（ノイズになる）:

> 方針変更や停止はいつでもメッセージでどうぞ（返信は不要です）

## 指摘・問題の3分類（トリアージ）

レビュー指摘・監査指摘・開発中に見つかった問題は、次の3分類で処理する:

1. **既存ルール内で低リスク・可逆** → 自律的に修正し、検証（テスト・ツールチェーン）と再レビューを行う。**その修正が spec.md / design.md の記述と食い違うなら、同じタスクの中で両方を更新する**（追随を後回しにすると整合性監査がその食い違いを指摘し、監査の周を消費する）
2. **今のタスクの完了には不要だが、承認済みスコープ内の欠陥** → tasks.md に登録する。挿入位置は最終受け入れ検証タスクの直前。優先度・理由・検証可能な完了条件を付記し、「関連:」は該当 S-n（無ければ「指摘」と明記）。**スコープ外の改善はこの分類ではなく proposal 経路**（trail に記録 → 最終報告で採否を人間へ）
3. **完了に必須で、不可逆な操作・外部への影響・秘密情報（API キー・課金等）に関わる人間判断が必要** → **BLOCKED**。まず自力の解決（調査・代替実装）を試み、それでも人間の入力が要る場合のみ該当タスクを分離（tasks.md の行末に `⛔待ち: <入力>` を付記。**進行中 `[>]` のタスク全体が待ちになる場合は `[ ]` に戻してから付記する** — `[>]` のままだと Step 2 の「`[>]` 最優先」と「⛔ は飛ばす」が衝突して空回りする）して報告し、他のタスクを続行する（人間の返信を待ってブロックしない。ターン終了の可否は SKILL.md Step 6 が正）。報告は下記の書式

- 分類に迷ったら: 要件・公式資料・現在のベストプラクティスを確認して今回の状況に適合するか検証し、それでも不明なら安全側（②で後回し、または③）へ倒す
- **設計レベルの判断は BLOCKED にしない**（現行どおり自律処理: design.md 更新＋trail 記録して続行）
- 要件レビュー（02）では②は適用しない（承認前の要件はタスク化の対象でないため。対応物は 02 の「3周で収束しなければゲートで開示」）

## BLOCKED 報告の書式

```
⛔ BLOCKED: <タスク / 指摘>（この報告は返信を待たない — 選択式にせず、他のタスクを続行する）
背景: <1〜2行>
選択肢: A) <案> / B) <案>
影響: A) <影響> / B) <影響>
推奨: <案> — <理由>
お願い: <人間がすること。秘密情報なら置き場所と作り方まで書く。例: 「キーは <取得先 URL>（所要 5 分程度）で取得できます。取得したら、アプリのフォルダ `~/code/my-app` の直下にターミナルで `echo 'WEATHER_API_KEY=値' >> .env`（「値」の部分を取得したキーに置き換えて）と打って保存し（既に `.env` があっても行が追加されるだけです）、『入れました』と返信してください。原則キーはチャットに貼らないでください。難しければ、キーを添えて『代わりに置いて』と送っていただければ、こちらで `.env` に書き、記録には残しません」>
```

## 検証キャップ超過・停止の報告書式

受け入れ検証が最大周で収束しなかったとき（05）:

```
⚠️ 検証が <n> 周で合格しませんでした: <不合格の基準（平たく）>
試したこと: <1〜3行>
お願い: 下の選択肢からお選びください
  A) ヒントを添えて再挑戦させる（例: 「別の天気 API を使って」）
  B) この基準を外す・緩める → 要件定義書を直し、再度承認をお願いする流れになります
  C) 別の方法の指示
  D) おまかせ（こちらの推奨で進めます: <A/B/C のどれを・なぜ推すか1行>）
（「進めて」だけでは検証をやり直さず、この報告に戻ります）
```

この4択は **AskUserQuestion** で提示する（A と C は具体の指示が要るので、選択肢の説明に「その他」で書ける旨を添える。本文は上の書式で出し、選択肢を二重に書かない）。**A / C が本文（ヒント・指示）無しで選ばれたら、1回だけ「ヒントまたは指示をまとめて送ってください」と聞き、届くまで再突入しない**（内容の無い A/C は起算点にせず、対応記録「本文待ち」を追記する）。**D が選ばれたら、⚠️ 本文に書いた推奨（A/B/C のいずれか）として扱う**（推奨 A/C なら推奨に書いたヒントを本文とみなして修正タスクを登録、推奨 B なら承認リセット）。

検証タスクを除く全残タスクが人間待ち（BLOCKED）で止まるとき（05 Step 2 / 最終受け入れ検証のガード0 と 3）:

```
⏸ あなたの作業待ちで止まりました: <残りタスクと待っている入力（例: T-4 — 天気 API キー）>
お願い: <該当 BLOCKED の「お願い」行を再掲>
```

停止指示に応じたとき:

```
⏸ 止めました: <どこまで完了したか（例: T-5 まで完了、T-6 は着手前に戻しました）>
再開するときは「進めて」（または「続きから」）と送ってください
```

hotl-pm 配下では、受領応答（「受け付けました」）と停止時の ⏸ は PM が出す（hotl-pm SKILL.md Step 4）。hotl がメインループで停止に応じた場合のみ hotl の ⏸。

## 割り込みへの対応

実行中にユーザーからメッセージが来た場合:

0-1. **処理を始める前に、まずメッセージの内容（依頼・指摘・変更内容）を trail に `interrupt` として記録する**（クラッシュしても人間の入力を失わないため。秘密情報の値は伏せ字 — 上記「人間向け文面の共通規則」）
0-2. **状況確認と単純な質問**（「いまどうなってる？」「これ Python？」）**は作業を止めない**: 1〜2行で答えて**そのまま続行する**（ターンを終えない。SKILL.md Step 6 の「状況確認クエリへの応答」は、**ターンの起動メッセージが状況確認だった場合**〔Step 5〕を指す）。状況確認は trail への記録不要。質問は 0-1 の記録に対応記録「質問に回答済み」を追記する。
1. 内容を判断する。**人間待ち（⛔ / ⚠️）への回答**（「入れました」等）なら、その入力が実際にあるか確認して（例: `.env` の `WEATHER_API_KEY`）「確認しました。T-4 を再開します」と返し、対応記録「入力確認済み」を追記する（環境の確認〔不正状態・docs 衝突・入れ子リポジトリ〕への回答も同様）。無ければその旨と「お願い」行を再掲し、対応記録「本文待ち」を追記する（入力が確認できるまで再開しない）（⚠️ キャップ超過への A/B/C/D の回答は 05「最終受け入れ検証」の手順4-3 へ渡す）。**進行の停止指示**なら現在のタスクを安全に閉じ（WIP は破棄せず残す。破棄するなら `decision` を記録）、state を保存し、上記「検証キャップ超過・停止の報告書式」の ⏸ で報告し、対応記録「停止済み」を追記する
2. **方針変更（仕様・設計・タスクレベル）**なら、影響範囲の判断を trail に記録した上で、該当ドキュメント（spec / design / tasks）と state（`updated_at`。phase は変えない）を更新して続行する。**タスクを追加する場合の挿入位置は②と同じ**（未チェックの最終受け入れ検証タスクの直前。末尾に足すと検証タスクが末尾でなくなり、検証を受けないタスクのまま done に到達する）。**反映先のドキュメントがまだ無い場合**は、直近の上流成果物に制約として書き、下流のフェーズがそれを読んで従う（`specification` 中の設計レベルの変更 → `spec.md` の「前提・制約」。`hearing` / `requirements` / `awaiting_approval` 中の仕様・設計レベルの変更 → `hearing-notes.md` の該当節に記録し、要件化の際に前提・制約へ運ぶ）。人間には1〜2行返す: 「受け付けました: <要旨> — <仕様 / 設計 / 作業手順>レベルの変更として反映して続行します」（要件レベルなら次項の後退報告がこれを兼ねる。委譲実行モードでは出さず trail 記録のみ — PM の受領応答が兼ねる）。反映後に対応記録「反映済み」を追記する
3. **要件レベルの変更（要件の追加・削除・意味の変更）**は承認済みハッシュを無効化する。**開発中の追加要望は差分ヒアリング（コンセプト提案・非ゴール確認）を省き、02 の差分更新＋再承認で扱う**（進行中の実装を止める往復を増やさないため。`done` 後の新要望はヒアリングに戻る — SKILL.md Step 4 の「イテレーション」項目）。SKILL.md の**承認リセット**（次 phase: `requirements`。`approved` が false の `requirements` 中ならリセット不要で 02 の差分更新のみ。phase が `done` なら SKILL.md Step 4 の「イテレーション」に従い `hearing`）を実行し、要件を更新して**承認ゲートを再実行**する（SKILL.md Step 7 の例外に対応。要件への反映後に対応記録「修正済み」を追記する）
