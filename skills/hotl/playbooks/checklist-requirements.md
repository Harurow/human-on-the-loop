# 要件レビューチェックリスト

レビュアーへ: あなたの仕事は**指摘のみ**。修正はしない。各項目を requirements.md 全体に適用し、指摘リストを返す。

## 1. 矛盾

- [ ] 要件同士が衝突していないか（片方を満たすと他方が満たせない組み合わせ）
- [ ] 機能要件が非ゴール・前提・制約と衝突していないか
- [ ] 非機能要件（性能等）が機能要件の実現を不可能にしていないか

## 2. 曖昧さ

- [ ] 定量化されていない形容が残っていないか。**禁止語**: 「など」「等」「適切に」「柔軟に」「高速に」「使いやすい」「シンプルに」「いい感じに」
- [ ] 主語のない要件がないか（誰が/何が行うのか）
- [ ] 複数解釈できる文がないか

## 3. テスト可能性

- [ ] 非機能要件に**性能目標・費用上限・セキュリティ前提・データ保全・運用**の5観点が揃っているか（「なし（理由）」の行にも受け入れ基準があるか。検証可能な基準を書けない観点は受け入れ基準「該当なし（理由）」を許容する。「なし」「該当なし」自体は禁止語に該当しない）
- [ ] 性能目標が数値目標を持つ場合、想定データ量（規模）の前提があるか（無いと計測条件が定まらない）
- [ ] 前提・制約（実行環境・既存資産・外部サービス）の各種別が記入または「なし」になっているか
- [ ] すべての要件（R-n / NR-n）に受け入れ基準があるか
- [ ] 各受け入れ基準は、第三者が読んで合否判定できるか
- [ ] **「すべての」「一切」「いかなる場合も」など全称・全数を要求する基準は、検査対象の集合を有限に列挙できるか**（例: 「全エラーメッセージが日本語」は、環境側の失敗経路〔文字コード・パイプ切断・書き込み失敗〕まで含むと無限に広がり、**修正しても合格を示せない**。「通常操作で出るエラーメッセージ」のように適用範囲を限定するか、対象を列挙する）
- [ ] 「〜できること」だけで終わり、条件・期待結果がない基準はないか

## 4. MECE

- [ ] **漏れ**: ヒアリングノートに記載があるのに要件に反映されていない事項はないか（ノートが渡されていない場合はこの項目をスキップと明記）
- [ ] **重複**: 同じことを言っている要件が複数ないか
- [ ] **スコープ外の混入**: 非ゴールに該当する要件が紛れていないか

## 判定の出力書式

```
判定: PASS / FAIL
指摘:
1. [矛盾|曖昧|テスト可能性|MECE] <対象 ID>: <指摘内容>（修正の方向性: <一言>）
2. ...
```

指摘ゼロなら PASS。1件でもあれば FAIL。
