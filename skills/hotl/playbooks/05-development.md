# Phase: 開発（自律区間）

**入力**: `docs/design.md`
**成果物**: 動くアプリ ＋ `docs/tasks.md`

## Step 1: タスク分解 / バックログ整合

`docs/tasks.md` の状態で分岐する:

- **無い（初回）** → 下記の書式で生成する
- **既存で、前回の development 以降に要件・仕様・設計が変更されていない（単純再開）** → 生成も変更もせず Step 2 の先頭未チェックタスクから再開する（テンプレートから作り直すと進捗台帳を破壊する）
  - **判定方法**: log.md の直近エントリと `git log --oneline -- docs/` を確認し、tasks.md の最終更新以降に requirements / spec / design の変更 commit があれば「変更あり」としてバックログ整合を行う
- **既存で、要件変更または イテレーションを経て再突入した** → **バックログ整合**を行う:
  1. 「最終受け入れ検証」タスクが `[x]` 済みなら、新たな最終受け入れ検証タスクを末尾に再追記する（このタスク無しで done に到達してはならない）
  2. 追加・変更された仕様 (S-n) に対応するタスクを、**未チェックの最終受け入れ検証タスクの直前**に挿入する（不変条件: 検証タスクは常にバックログ末尾の未チェックであり続ける）
  3. 削除された要件・仕様に対応するタスクを処理する:
     - 未チェック（`[ ]`）→ `[-]`（キャンセル）にして理由を付記する（実装しない）
     - 進行中（`[>]`）→ WIP の破棄 / 引き継ぎを判断して trail に記録した上で `[-]` 化する
     - **チェック済み（`[x]`）→ 実装が既に存在するので、それを取り除く「除去タスク」を 2 と同じ位置に追加する**（完了条件: 該当機能・コード・テストが除去され、残りのテストが通ること）
  4. **カバレッジ確認**: spec.md の全仕様 (S-n) がいずれかのタスク（`[x]` 済み含む）の「関連」に現れることを確認する。漏れがあればタスクを追加する
  5. 整合内容を log.md に記録して commit する

初回は、スキルの `templates/tasks.md` の書式で `docs/tasks.md` を生成する（テンプレートのガイドコメントは成果物に残さない）:

- 各タスク: `T-n: <タスク名> — 完了条件: <検証可能な条件> ／関連: S-n`
- 粒度は**半日以下**。大きすぎるタスクは分割する
- 実装順（依存の少ない順）に並べる。最初のタスクは通常「プロジェクトの雛形・ビルド・テスト実行環境の構築」
- 最後のタスクは「最終受け入れ検証（本 playbook の同名節に従って実施）」

生成したら**カバレッジ確認**（spec.md の全 S-n がいずれかのタスクの「関連」に現れること）を行い、commit してタスク数を中間報告する。

## Step 2: 実装ループ

実装はメインループで行う（コードベースの知識をタスク間で持ち越すため、タスクごとにサブエージェント分割しない）。
**着手前に `docs/lessons.md`（知見台帳）を確認し、封印済みの方法を避ける**（下記「自律的改善」参照。ファイルが無ければ確認不要）。

tasks.md の**先頭の未完了タスク**（`[>]` 進行中があればそれを最優先、無ければ先頭の `[ ]`）から順に:

1. **着手**: タスクの `[ ]` を `[>]`（進行中）にする
2. **実装**: design.md のモジュール構成に従う。既存コードの慣習に合わせる
3. **検証**: テスト戦略に従いテストを書き、design.md の検証ツールチェーン（formatter / linter / 型検査 / テスト / ビルド等、導入済みのもの一式）を実行して通す
4. **セルフレビュー**: diff を読み直し、タスクの完了条件と照合する
5. **コードレビュー**: fresh context のレビュアーに「タスクの diff」「関連 S-n の仕様抜粋」「design.md の該当モジュール節」「スキルの `playbooks/checklist-code.md`」**のみ**を渡してレビューさせる（会話履歴は渡さない。サブエージェントが使えなければ同じ入力制約でインラインに適用）。指摘は `reporting.md` の3分類で処理し、①の修正後の再レビューは**1周まで**（収束しない指摘は②か③へ）。**省略条件**: 数行の機械的変更（typo・定数・コメント）はレビューをスキップしてよい
6. **チェック＆commit**: 完了条件の確認は実行結果・テスト出力という**証拠**で行い、その要旨を trail に記録する（**推測だけを根拠に完了しない**）。tasks.md の `[>]` を `[x]` にし、行末に `（完了: YYYY-MM-DD HH:MM）` を付記（`date` から取得）して git commit（メッセージにタスク ID を含める）
7. 次のタスクへ

**報告リズム**: タスク3件完了ごと、またはブロッカー発生時に `reporting.md` の中間報告書式で報告する（実行は止めない）。

## 再開性の維持

- **再開時はまず `git status` で未コミット変更を確認する**。中断したタスクの作業途中（WIP）が残っていたら、タスクの完了条件と照合して「引き継ぐ」か「破棄してやり直す」かを判断し、判断を log.md に記録してから進む
- セッションがいつ切れても、新しいセッションが tasks.md から再開できる状態を常に保つ（`[>]` 進行中タスクがあればそこから、無ければ先頭の `[ ]` から）
- 中途半端な状態で commit しない。タスクが完了できない場合は、そのタスクを分割して完了できた部分だけチェックする
- 設計変更が必要になったら design.md を更新し、理由を log.md に記録してから続行する

## 自律的改善（計測して選ぶ）

作業方法そのものを改善対象にする。判断の結果は `docs/lessons.md`（知見台帳。最初の知見を書くときに作成）に蓄積する:

- **計測比較**: 方法の優劣（速度・成功率・単純さ）が結果に効きそうで複数の選択肢がある場合、小さく両方を試して客観指標で比較し、良い方を採択する。ただし**比較にかけるコストが期待される節約を超えないこと**（自明な優劣は計測しない）
- **2回失敗ルール**: 同じ方法で2回失敗したら、方法自体を疑って代替を試す
- **失敗も記録**: 方法の失敗は**1回目から** trail に `finding` として記録する（セッションを跨いで2回失敗ルールを数えられるように。カウントは trail を正とする）。計測実験の開始・結果も trail に残し、実験途中でセッションが切れたら trail から再開する
- **封印**: 退けた方法は「なぜダメだったか」と**再試行条件**（状況の変化・新情報）を lessons.md に記録し、**条件が満たされない限り再び使わない**
- 採択の判断は trail に `decision` として記録し、詳細を lessons.md に書く

lessons.md の書式:

```markdown
# 知見台帳: <app-name>

## L-1: <テーマ（例: テスト実行方法）>
- 採択: <方法A> ／ 退けた: <方法B>
- 計測: <指標と値（例: A 3.2s / B 11.5s）。計測不要の判断ならその根拠>
- 理由: <なぜ退けた方がダメだったか>
- 再試行条件: <退けた方を再検討してよい状況。無ければ「なし」>
```

## 開発中に見つけた改善アイデア

スコープ外の改善アイデア（リファクタ・追加機能・UX 改善）は**黙って実装しない**（スコープクリープ）。
trail に `proposal` として記録し、最終報告の「改善提案」で提示する。次イテレーションの候補になる。

## ブロッカーの扱い

- 自力で解決を試みる（調査・代替実装）。人間の返信を待ってブロックしない
- どうしても人間の入力が必要な場合（アカウント・API キー・課金等）のみ、そのタスクをスキップ可能な形に分離して報告し、他のタスクを続行する

## 最終受け入れ検証

tasks.md の最後のタスクとして（他の全タスク完了後に）実施する。このタスク内で監査 → 検証の順に行う:

1. **整合性監査**: fresh context の監査者に「docs/ 一式」と「`git log --oneline` の出力」のみを渡し、次を指摘させる: (a) 成果物間の矛盾・古い参照・正本の重複、(b) trail の finding / interrupt / proposal で未処理のまま残っているもの、(c) state.json・tasks.md・git 履歴の食い違い。指摘は `reporting.md` の3分類で処理する
2. **受け入れ検証**: fresh context の検証者に「`docs/requirements.md` の受け入れ基準」と「成果物（リポジトリ）」のみを渡し、基準を1件ずつ実際に動かして合否判定させる（作成者バイアスの排除）。サブエージェントが使えなければ、いずれも同じ入力制約で自分が実行結果を添えて照合する
3. **不合格・未処理があれば**: 検証タスクは `[ ]`（または `[>]`）のままにし、修正タスクを**検証タスクの直前**に挿入して Step 2 に戻る（検証タスクは常にバックログ末尾の未完了であり続け、修正 → 再監査・再検証の順が保たれる）
4. 全合格したら結果を log.md に記録し、検証タスクを `[x]` にする

## 完了

**done へ遷移できる前提**: tasks.md の全タスクが `[x]` または `[-]` で、最後の「最終受け入れ検証」タスクが `[x]` であること。
**振り返り**: 遷移の前に開発全体を振り返り、次イテレーションに効く知見（効果的だった方法・時間を食った原因）があれば lessons.md に追記する（無理に書かない。1〜3件まで）。
SKILL.md Step 6 を実行（次 phase: `done`）。**このときの報告が最終報告を兼ねる**（別途重ねて報告しない）: 何ができたか／使い方・起動方法／既知の制限／受け入れ基準の検証結果／改善提案（trail の `proposal` エントリがあれば）。
