# Phase: 開発（自律区間）

**入力**: `docs/design.md`
**成果物**: 動くアプリ ＋ `docs/tasks.md`

## Step 1: タスク分解 / バックログ整合

`docs/tasks.md` の状態で分岐する:

- **無い（初回）** → 下記の書式で生成する
- **既存で、前回の development 以降に要件・仕様・設計が変更されていない（単純再開）** → 生成も変更もせず Step 2 の先頭未チェックタスクから再開する（テンプレートから作り直すと進捗台帳を破壊する）
  - **判定方法**: log.md の直近エントリと `git log --oneline -- docs/` を確認し、tasks.md の最終更新以降に requirements / spec / design の変更 commit があれば「変更あり」としてバックログ整合を行う
- **既存で、要件変更または イテレーションを経て再突入した** → **バックログ整合**を行う:
  1. 追加・変更された仕様 (S-n) に対応するタスクを末尾に追記する
  2. 削除された要件・仕様に対応する**未チェックタスクは実装しない**: `- [ ]` を `- [-]`（キャンセル）にして理由を付記する
  3. 「最終受け入れ検証」タスクが `[x]` 済みなら、新たな最終受け入れ検証タスクを末尾に再追記する（このタスク無しで done に到達してはならない）
  4. 整合内容を log.md に記録して commit する

初回は、スキルの `templates/tasks.md` の書式で `docs/tasks.md` を生成する:

- 各タスク: `T-n: <タスク名> — 完了条件: <検証可能な条件> ／関連: S-n`
- 粒度は**半日以下**。大きすぎるタスクは分割する
- 実装順（依存の少ない順）に並べる。最初のタスクは通常「プロジェクトの雛形・ビルド・テスト実行環境の構築」
- 最後のタスクは「最終受け入れ検証（本 playbook の同名節に従って実施）」

生成したら commit し、タスク数を中間報告する。

## Step 2: 実装ループ

実装はメインループで行う（コードベースの知識をタスク間で持ち越すため、タスクごとにサブエージェント分割しない）。

tasks.md の**先頭の未チェックタスク**から順に:

1. **実装**: design.md のモジュール構成に従う。既存コードの慣習に合わせる
2. **テスト**: テスト戦略に従いテストを書き、実行して通す
3. **セルフレビュー**: diff を読み直し、タスクの完了条件と照合する
4. **チェック＆commit**: tasks.md の `[ ]` を `[x]` にし、git commit（メッセージにタスク ID を含める）
5. 次のタスクへ

**報告リズム**: タスク3件完了ごと、またはブロッカー発生時に `reporting.md` の中間報告書式で報告する（実行は止めない）。

## 再開性の維持

- **再開時はまず `git status` で未コミット変更を確認する**。中断したタスクの作業途中（WIP）が残っていたら、タスクの完了条件と照合して「引き継ぐ」か「破棄してやり直す」かを判断し、判断を log.md に記録してから進む
- セッションがいつ切れても、新しいセッションが tasks.md の先頭未チェックタスクから再開できる状態を常に保つ
- 中途半端な状態で commit しない。タスクが完了できない場合は、そのタスクを分割して完了できた部分だけチェックする
- 設計変更が必要になったら design.md を更新し、理由を log.md に記録してから続行する

## ブロッカーの扱い

- 自力で解決を試みる（調査・代替実装）。人間の返信を待ってブロックしない
- どうしても人間の入力が必要な場合（アカウント・API キー・課金等）のみ、そのタスクをスキップ可能な形に分離して報告し、他のタスクを続行する

## 最終受け入れ検証

tasks.md の最後のタスクとして（他の全タスク完了後に）実施する:

1. サブエージェントが使える場合、**fresh context の検証者**に「`docs/requirements.md` の受け入れ基準」と「成果物（リポジトリ）」のみを渡し、基準を1件ずつ実際に動かして合否判定させる（作成者バイアスの排除）。使えなければ自分で1件ずつ、実行結果を添えて照合する
2. **不合格があれば**: 検証タスクは `[ ]` のままにし、修正タスクを**検証タスクの直前**に挿入して Step 2 に戻る（検証タスクは常にバックログ末尾の未チェックであり続け、修正 → 再検証の順が保たれる）
3. 全合格したら結果を log.md に記録し、検証タスクを `[x]` にする

## 完了

**done へ遷移できる前提**: tasks.md の全タスクが `[x]` または `[-]` で、最後の「最終受け入れ検証」タスクが `[x]` であること。
SKILL.md Step 6 を実行（次 phase: `done`）。**このときの報告が最終報告を兼ねる**（別途重ねて報告しない）: 何ができたか／使い方・起動方法／既知の制限／受け入れ基準の検証結果。
