# Phase: 開発（自律区間）

**入力**: `docs/design.md`
**成果物**: 動くアプリ ＋ `docs/tasks.md`

## Step 1: タスク分解 / バックログ整合

`docs/tasks.md` の状態で分岐する:

- **無い（初回）** → 下記の書式で生成する（trail に未対応の `finding` があればタスク化して含め、対応記録「②でタスク化」を追記する）
- **既存で、下のバックログ整合の条件に当たらない（単純再開）** → 生成も変更もせず Step 2 の選定ルール（`[>]` 最優先）に従って再開する（テンプレートから作り直すと進捗台帳を破壊する）
  - **判定方法**（整合の条件を先に評価する）: `git log --oneline -- docs/requirements.md docs/spec.md docs/design.md` で tasks.md の最終 commit より後に変更 commit がある、**または** tasks.md の最終 commit より後に `hotl: done -> development` の遷移 commit がある（state.json の `phase_history` でも確認できる）なら「整合が必要」（ただしその遷移 commit より後に log.md の整合記録があれば済んでいる）。どちらも無ければ単純再開
- **既存で、要件変更・イテレーション・不具合報告（`done` から戻った）・⚠️ 後の A/C 回答（対応記録の無い `interrupt`）を経て再突入した** → **バックログ整合**を行う（不具合報告の場合は、trail の当該 `interrupt` に書かれた不合格の基準に対する修正タスクを追加し〔検証タスクは下の手順1で再追記〕、その interrupt に対応記録「対応: T-n として登録」を追記する）（**再入可能に**: 追記・挿入の前に、同内容のタスクや未完了の検証タスクが既に存在しないか確認する。整合途中のクラッシュ再開で重複させない）:
  1. 「最終受け入れ検証」タスクが `[x]` 済みなら、新たな最終受け入れ検証タスクを末尾に再追記する（このタスク無しで done に到達してはならない）
  2. 追加・変更された仕様 (S-n) に対応するタスクを、**未チェックの最終受け入れ検証タスクの直前**に挿入する（不変条件: 検証タスクは常にバックログ末尾の未チェックであり続ける）
  3. 削除された要件・仕様に対応するタスクを処理する:
     - 未チェック（`[ ]`）→ `[-]`（キャンセル）にして理由を付記する（実装しない）
     - 進行中（`[>]`）→ WIP の破棄 / 引き継ぎを判断して trail に記録した上で `[-]` 化する
     - **チェック済み（`[x]`）→ 実装が既に存在するので、それを取り除く「除去タスク」を 2 と同じ位置に追加する**（完了条件: 該当機能・コード・テストが除去され、残りのテストが通ること）
  4. **カバレッジ確認**: spec.md の全仕様 (S-n) がいずれかのタスク（`[x]` 済み含む）の「関連」に現れることを確認する。漏れがあればタスクを追加する（2・3 と同じく最終受け入れ検証タスクの直前に挿入）
  5. 整合内容を log.md に記録して commit する

初回は、スキルの `templates/tasks.md` の書式で `docs/tasks.md` を生成する:

- 各タスク: `T-n: <タスク名> — 完了条件: <検証可能な条件> ／関連: S-n`
- 粒度は**半日以下**。大きすぎるタスクは分割する
- 実装順（依存の少ない順）に並べる。最初のタスクは通常「プロジェクトの雛形・ビルド・テスト実行環境の構築（.gitignore を技術スタックに合わせて拡充し、formatter / linter の対象から `docs/` を除外することを含む）」
- 最後のタスクは「最終受け入れ検証（本 playbook の同名節に従って実施）— 完了条件: 全受け入れ基準の合格 ／関連: 全要件」

生成したら**カバレッジ確認**（spec.md の全 S-n がいずれかのタスクの「関連」に現れること）を行い、commit して「🔨 開発開始: 全 N タスク」と中間報告する。**tasks.md が存在するが未コミット**（`git status` で untracked）なら初回生成直後のクラッシュなので、このカバレッジ確認と commit から再開する（Step 1 冒頭の分岐より優先）。

## Step 2: 実装ループ

実装はメインループで行う（コードベースの知識をタスク間で持ち越すため、タスクごとにサブエージェント分割しない）。
**着手前に `docs/lessons.md`（知見台帳）を確認し、封印済みの方法を避ける**（下記「自律的改善」参照。ファイルが無ければ確認不要）。

tasks.md の**先頭の未完了タスク**（`[>]` 進行中があればそれを最優先、無ければ先頭の `[ ]`。行末に `⛔待ち:` 注記のある BLOCKED タスクは飛ばし、人間待ちへの回答で解除されたら注記を消す）から順に。**BLOCKED が1件以上あり、検証タスクを除く未完了がそれだけになったら** reporting.md の「あなたの作業待ちで止まりました」書式で報告してターンを終了する（検証タスクには進まない）:

1. **着手**: タスクの `[ ]` を `[>]`（進行中）にする
2. **実装**: design.md のモジュール構成に従う。既存コードの慣習に合わせる
3. **検証**: テスト戦略に従いテストを書き、design.md の検証ツールチェーン（formatter / linter / 型検査 / テスト / ビルド等、導入済みのもの一式）を実行して通す
4. **セルフレビュー**: diff を読み直し、タスクの完了条件と照合する
5. **コードレビュー**: fresh context のレビュアーに「タスクの diff」「tasks.md の該当タスク行（完了条件を含む）」「関連 S-n の仕様抜粋」「design.md の該当モジュール節」「要件の費用上限行（NR。あれば）」「スキルの `playbooks/checklist-code.md`」**のみ**を渡してレビューさせる（会話履歴は渡さない。サブエージェントが使えなければ同じ入力制約でインラインに適用）。指摘は `reporting.md` の3分類で処理し、①の修正後の再レビューは**1周まで**（収束しない指摘は②か③へ）。**省略条件**: 数行の機械的変更（typo・定数・コメント）はレビューをスキップしてよい
6. **チェック＆commit**: 完了条件の確認は実行結果・テスト出力という**証拠**で行い、その要旨を trail に記録する（**推測だけを根拠に完了しない**）。tasks.md の `[>]` を `[x]` にし、行末に `（完了: YYYY-MM-DD HH:MM）` を付記（`date` から取得）して git commit（そのタスクで変更したファイルを明示指定。`git add -A` は使わない。メッセージにタスク ID を含める）
7. 次のタスクへ

**報告リズム**: タスク3件完了ごと、またはブロッカー発生時に `reporting.md` の中間報告書式で報告する（実行は止めない）。

## 再開性の維持

- **再開時はまず `git status` で未コミット変更を確認する**。中断したタスクの作業途中（WIP）が残っていたら、タスクの完了条件と照合して「引き継ぐ」か「破棄してやり直す」かを判断し、判断を log.md に記録してから進む
- セッションがいつ切れても、新しいセッションが tasks.md から再開できる状態を常に保つ（`[>]` 進行中タスクがあればそこから、無ければ先頭の `[ ]` から）
- 中途半端な状態で commit しない。タスクが完了できない場合は、そのタスクを分割して完了できた部分だけチェックする
- 設計変更が必要になったら design.md を更新し、理由を log.md に記録してから続行する

## 自律的改善（計測して選ぶ）

作業方法そのものを改善対象にする。判断の結果は `docs/lessons.md`（知見台帳。最初の知見を書くときに作成）に蓄積する:

- **計測比較**: 方法の優劣（速度・成功率・単純さ）が結果に効きそうで複数の選択肢がある場合、小さく両方を試して客観指標で比較し、良い方を採択する。ただし**比較にかけるコストが期待される節約を超えないこと**（自明な優劣は計測しない）
- **2回失敗ルール**: 同じ方法で2回失敗したら、方法自体を疑って代替を試す
- **失敗も記録**: 方法の失敗は**1回目から** trail に `decision`（方法試行の結果）として記録する（セッションを跨いで2回失敗ルールを数えられるように。カウントは trail を正とする。`finding` にしないのは、監査の「未処理 finding」判定に誤検出されないため）。計測実験の開始・結果も trail に残し、実験途中でセッションが切れたら trail から再開する
- **封印**: 退けた方法は「なぜダメだったか」と**再試行条件**（状況の変化・新情報）を lessons.md に記録し、**条件が満たされない限り再び使わない**
- 採択の判断は trail に `decision` として記録し、詳細を lessons.md に書く

lessons.md の書式:

```markdown
# 知見台帳: <app-name>

## L-1: <テーマ（例: テスト実行方法）>
- 採択: <方法A> ／ 退けた: <方法B>
- 計測: <指標と値（例: A 3.2s / B 11.5s）。計測不要の判断ならその根拠>
- 理由: <なぜ退けた方がダメだったか>
- 再試行条件: <退けた方を再検討してよい状況。無ければ「なし」>
```

## 開発中に見つけた改善アイデア

スコープ外の改善アイデア（リファクタ・追加機能・UX 改善）は**黙って実装しない**（スコープクリープ）。
trail に `proposal` として記録し、最終報告の「改善提案」で提示する。次イテレーションの候補になる。

## 最終受け入れ検証

tasks.md の最後のタスクとして（他の全タスク完了後に）実施する。このタスク内で監査 → 検証の順に行う:

0. **着手・再着手時のガード**: 検証タスクより前に未完了タスクがあれば、trail の直近の着手エントリに終了記録が無いなら「検証タスク T-n 周 k 中断（ガード）」を `report` で記録した上で、検証タスクを `[ ]` に戻して Step 2 へ（挿入と `[ ]` 戻しの間でクラッシュしても、このガードが吸収する。ただし前の未完了が `⛔待ち:` のみなら、reporting.md の「あなたの作業待ちで止まりました」書式で報告してターンを終了する）。ガードを通過したら**周の記録**を次の順で決める:
   - **起算点**: 当該 T-n の生成、承認リセット（要件変更・イテレーション）、または対応記録「T-n として登録」を持つ `interrupt`。起算点より後に着手エントリが無ければ**周 1**として「検証タスク T-n 着手 周 1」を `report` で記録する
   - 直近の着手エントリに終了記録（中断・手順4の ⚠️・手順5の完了）が無ければ**同じ周 k の続き**（クラッシュ再開）。新しい着手エントリは書かない
   - 直近の終了記録が ⚠️ で、その後に起算点が無ければ着手せず手順4-3（⚠️ の再提示）へ
   - それ以外は「検証タスク T-n 着手 周 k+1」を記録する
   **周番号の正はこの着手エントリだけ**。各役割（監査・UX ウォークスルー・受け入れ検証）のキャップは「起算点以降にその役割が完了した周の数」で数える（コード修正で周が進んでも、その役割を実施していない周は数えない）

1. **整合性監査**: fresh context の監査者に「docs/ 一式」「`git log --oneline` の出力」「reporting.md の「対応の記録」節（未処理の判定基準）」のみを渡し、次を指摘させる: (a) 成果物間の矛盾・古い参照・正本の重複、(b) trail の finding / interrupt のうち**対応記録の無い**もの（proposal は最終報告まで pending が正常なので対象外）、(c) state.json・tasks.md・git 履歴の食い違い。指摘は `reporting.md` の3分類で処理する
   - **収束キャップ（監査）**: 監査は再突入時を含め**最大2周**。各周の開始・完了（キャップによるスキップも）を、**対象の検証タスク ID (T-n) と周番号 k を付けて** trail に `report` として記録する（周内でその役割を実施済みかを判定する正。完了＝指摘リストを trail に記録した時点。完了エントリの無い開始エントリはその周内でやり直す — 新しい開始エントリは追加しない。周番号自体はガード0の着手エントリが正）。2周目は前回の監査指摘と対応記録を併せて渡し、**新規の指摘のみ**を扱う。2周で収束しなければ残指摘を最終報告で人間に開示して先へ進む（02 のエスケープと同型）
   - **却下してよい**: 指摘が誤り・対応不要と判断した場合は、判断と根拠を trail に `decision` として記録して却下できる
   - **①指摘の修正方法**: コード変更を伴う修正は手順3（修正タスク挿入）で行い、Step 2 のループ（ツールチェーン・コードレビュー・証拠）を通す。ドキュメントのみの修正はインラインでよい（**requirements.md を除く** — SKILL.md 共通規則「承認済み要件の凍結」）
1.5. **UX ウォークスルー（利用者視点レビュー）**: 画面・出力を持つ成果物では、受け入れ検証の**前**に、fresh context のレビュアーに「要件のユーザー像・利用シーン・成功基準」と「動作中の成果物（実 URL または起動手順）」**のみ**を渡し、**コードを読まずに実際の画面を利用者として使って**評価させる。手順: 主要画面を実端末相当の幅（スマホ幅・PC 幅）× 配色モード（ライト・ダーク。対応する場合）でスクリーンショットに保存し、画像を実際に見ながら利用シーンの手順をなぞる — 「開いた瞬間に知りたいことが分かるか」「次の操作に迷わないか」「文字量・略記・用語」「一目で判別できる強調（色・順序）」「情報の順序（新しいものが上か）」「横スクロール・折り返し崩れ」。出力は「必ず直すべき（done の前）／次イテレーション／良い点」の3区分（根拠のスクリーンショット名付き・利用者の言葉で・実装用語を使わない）。指摘は `reporting.md` の3分類で処理し（「必ず直すべき」は①または②で検証タスクの直前に挿入）、結果は「必ず直すべき」を `finding`、「次イテレーション」を `proposal`（done の最終報告で回収）として trail に記録し、周の要約を `report` として記録し、05「完了」の最終報告に「UX ウォークスルーの結果」として含める。**受け入れ基準の合格は機能の正しさしか保証しない** — 使う人が見つけるはずの不満をここで先に拾う。再周はガード0の周番号に従属し（最大3周。前回指摘＋対応後の画面で新規指摘のみ。前回以降に画面・出力の変更が無ければスキップしてよい — スキップも `report` に残す）、周の開始・完了を T-n と周番号 k 付きで `report` に記録する（再開時に実施済みかを判定する正）。サブエージェントが使えなければ同じ入力制約で自分が行い、スクリーンショットを撮る手段が無ければ出力テキスト・画面の DOM で代替してその旨を記録する
2. **受け入れ検証**: fresh context の検証者に「`docs/requirements.md` の受け入れ基準と前提・制約」と「成果物（リポジトリ）」のみを渡し、基準を1件ずつ実際に動かして合否判定させる（作成者バイアスの排除）。サブエージェントが使えなければ、いずれも同じ入力制約で自分が実行結果を添えて照合する。**非機能横断チェック**を同じ周で必ず含める（機能基準の合格だけで先へ進まない）:
   - (a) **セキュリティ**: 別の fresh レビュアーに「リポジトリ」「要件のセキュリティ前提（NR）」「design.md」「スキルの `playbooks/checklist-security.md`」のみを渡し、攻撃面の棚卸しと指摘を受ける。**検証タスク1つにつき原則1回**。再周は「前回指摘＋対応記録＋その後の修正 diff」を渡して**新規指摘のみ**を扱い、前回以降コード変更が無ければスキップしてよい。再周は受け入れ検証の周回（最大3周）に従属し、それ自体は独立に反復しない — 収束しなければ検証キャップの規則で開示に回す（再周の diff 基点を trail から復元できるよう、周の要約 `report` に対象 commit hash を含める）。指摘は `reporting.md` の3分類で処理する（監査と同じく、誤りと判断した指摘は `decision` を記録して却下できる。秘密情報のローテーション・履歴改変・認証追加など③や要件変更に当たるものは①にしない。要件のセキュリティ前提自体の不備に帰着する場合は承認リセット経由〔要件変更 → `requirements`〕）。セキュリティ前提行（既定 NR-3）の受け入れ判定は (a) を正とし、受け入れ検証者は NR のセキュリティ前提行を判定対象から外す
   - (b) **性能**: 受け入れ検証者が、数値基準を持つ NR を**実測**で判定する（推測・単体テストの通過だけでは合格にしない。計測条件と数値を trail に残す）。数値基準が無ければ「該当なし（合格）」と記録する
   - (c) **費用**: メインループが行う。月額換算 = **1実行あたりの実測使用量 × 想定実行頻度**（頻度が要件に無ければ設計の起動方式から既定頻度を置き、その旨を併記）。費用上限行（既定 NR-2）の受け入れ判定は (c) を正とし、受け入れ検証者は NR の費用上限行を判定対象から外す。判定:

     | 状況 | 記録 |
     |---|---|
     | 課金要素が無い（コード・design に外部課金の呼び出しが無い） | 該当なし（合格） |
     | 費用上限が「なし（外部課金なし）」なのに課金対象の呼び出しがある | 不合格（`finding`。前提違反） |
     | 費用上限あり | 月額換算 vs 上限で合否 |
     | 上限なし（NR-2 不在または「上限なし」） | 月額換算を「開示（合否対象外）」。完了判定〔全受け入れ基準の合格〕では合格扱い。「該当なし（合格）」にしない |

     使用量が記録されていなければそれ自体を指摘とする（NR-2 が無い凍結要件では使用量記録は承認スコープ外なので、指摘ではなく proposal として最終報告に載せる）
   - (d) **その他の NR**（データ保全・運用等）: 受け入れ検証者が通常の受け入れ基準として判定する（バックアップからの復元・失敗通知などは実際に実行して確認する）。受け入れ基準が「該当なし（理由）」の行は「該当なし（合格）」と記録する。**前提・制約**（実行環境・既存資産・外部サービス）も成果物と照合し、逸脱（例: 前提の環境で動かない）は `finding` にする
   - **承認済み要件に該当 NR が無い場合**（凍結中の要件は書き換えない）: 既定前提（性能基準なし・費用上限なし〔月額換算の開示のみ〕・公開範囲は spec/design に明記されたもの、無ければローカルのみ・データ保全と運用は判定対象なし）で照合し、結果と「要件に前提が無い」旨を最終報告で開示する。追補は次イテレーションの承認リセット経由
   - 記録: 各指摘は trail に `finding`（MINOR は「②でタスク化」または「最終報告で開示」を対応記録として別エントリで追記）、周の要約は `report`（対象 commit hash を含める）。05「完了」の最終報告に「非機能横断チェックの結果」として含める
3. **やり直しの条件（一般則）**: 監査・検証の過程で検証タスクより前に新たな未完了タスクが生じたら — 検証不合格の修正タスク、監査①指摘のコード修正タスク、②でタスク化した指摘、③で分離したタスク、**いずれも挿入位置は検証タスクの直前**（末尾不変条件を守る）— まず「検証タスク T-n 周 k 中断（修正タスク挿入）」を `report` で記録し、タスクを挿入し、**検証タスクを `[ ]` に戻して** Step 2 に戻る（`[>]` のまま残すと再開時の `[>]` 最優先ルールが挿入タスクを飛ばしてしまう。受け入れ検証が不合格で、その完了周が既に3なら本則ではなく手順4）。挿入前に同内容の**未完了**タスクが無いか確認する（過去に `[x]` 済みの同種修正があっても、別アプローチの新タスクとして挿入してよい）。これで先頭未完了＝挿入タスクとなり、修正 → 再監査（新規指摘のみ）・再検証の順が保たれる。③のみが残り、検証タスクを除く全残タスクが人間待ちになったら、同じく中断を記録して検証タスクを `[ ]` に戻し、reporting.md の「あなたの作業待ちで止まりました」書式で報告してターンを終了する
4. **収束キャップ（検証）**: 受け入れ検証は**最大3周**（受け入れ検証を完了した周の数。周番号はガード0の記録が正。周の開始・完了・やり直しの規則は監査と同じ）。3周目も全合格に至らない場合:
   1. **検証タスクを `[ ]` に戻す**（`[>]` のまま残さない）
   2. reporting.md「検証キャップ超過・停止の報告書式」の ⚠️ で報告し、ターンを終了する（Step 6 の「受け入れ検証のキャップ超過」に該当。**done へは遷移しない** — 受け入れ基準を満たさないまま完了扱いにしない）
   3. **人間の指示（interrupt 記録）を経て再突入したら、検証・監査の周回カウントは 0 から数え直す**（人間の介入がサイクルの区切り。A/C の回答はヒント・指示に基づく修正タスクを検証タスクの直前に挿入し、当該 interrupt に対応記録「T-n として登録」を追記してから再突入する。B は割り込み case 3〔承認リセット〕の経路。数え直しは UX ウォークスルーを含む全役割に及び、起点はガード0の起算点の定義に従う。ただし「対応: 再開」だけの interrupt〔中身の無い「進めて」〕は起点にしない — この場合は検証を再実行せず、同じ ⚠️ 報告を再提示してターンを終える）
5. **完了**: 全合格し、**かつ検証タスクより前に未完了タスクが残っていない**場合のみ、結果を log.md に記録して検証タスクを `[x]` にする

## 完了

**done へ遷移できる前提**: tasks.md の全タスクが `[x]` または `[-]` で、最後の「最終受け入れ検証」タスクが `[x]` であること。
**振り返り**: 遷移の前に開発全体を振り返り、次イテレーションに効く知見（効果的だった方法・時間を食った原因）があれば lessons.md に追記する（無理に書かない。1〜3件まで）。
SKILL.md Step 6 を実行（次 phase: `done`）。**このときの報告が最終報告を兼ねる**（別途重ねて報告しない。改変検知の再承認や不具合修正など前回の done 以降の変更が限定的な周回では、変更点と検証結果のみの差分版にする）: 何ができたか／**最初にあなたがすること**（`.env` の記入・スケジューラ登録等。BLOCKED 書式と同じく置き場所・手順・所要時間まで書く。無ければ「ありません」）／使い方・起動方法／既知の制限／受け入れ基準の検証結果／**非機能横断チェックの結果（セキュリティ・性能実測・費用実測 vs 上限）**／**UX ウォークスルーの結果**（利用者視点で拾った指摘と対応。1.5 を実施した場合）／改善提案（reporting.md「成果物を見せるときの改善提案」に従う。trail の pending な `proposal` もここで回収）／改善提案の採否の伝え方（reporting.md 同節）／末尾に **凍結中の要件への指摘**（開示のみ）と **却下した監査・セキュリティレビュー指摘**（あれば件数と要旨。詳細は log.md 参照 — 却下を人間から不可視にしない）。
