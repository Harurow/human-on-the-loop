# Phase: 要件定義

**入力**: `docs/hearing-notes.md`
**成果物**: `docs/requirements.md`（スキルの `templates/requirements.md` に従う）
**このフェーズの最後に、ワークフロー唯一のブロッキングポイントである承認ゲートがある。**

## 執筆

1. `docs/requirements.md` が**既に存在する場合**（修正依頼・イテレーション・再開）は再生成せず、変更点だけの差分更新にする。初回のみ、スキルの `templates/requirements.md` をコピーして雛形にする。既存ファイルにガイドコメントや未記入の `<...>` が残っていれば前回の書きかけなので、差分更新ではなく未完成部分を埋めて完成させる
2. ヒアリングノートの内容を要件に落とす:
   - 機能要件は必ず ID (R-1, R-2, ...) と受け入れ基準を付ける
   - 受け入れ基準は検証可能な形（誰が読んでも合否判定できる）で書く
   - 非ゴール節は必須。ヒアリングで合意した内容をそのまま書く
   - 各機能要件に**出所**（ユーザー / 提案）を記す。ヒアリングで**採用された**エージェント提案、または trail の `proposal` に採用が記録された提案のみ「提案」として要件化する（勝手な機能追加をしない）
3. **非機能要件の必須5観点**（性能目標・費用上限・セキュリティ前提・データ保全・運用）と**前提・制約**（実行環境・既存資産・外部サービス）を必ず埋める。ヒアリングノートに値が無ければ**質問で往復せず**、合理的な既定値を置いて出所を「提案」にし、承認ゲートの要約で「提案由来」として明示して確認を受ける。既定値の例: 費用上限は「想定実行頻度 × 1実行あたりの想定単価」の概算の1.5倍、想定実行頻度は採用コンセプトの形態から〔定期実行なら1日 n 回・対話型なら1日あたりの想定操作回数〕、想定データ量は利用シーンから概算、公開範囲はローカルのみ、データ保全は「ローカル保存のみ・消失許容」、運用は「失敗は次回実行時の標準出力で判明」、前提・制約は「なし」。非機能の「なし」行にも理由と受け入れ基準（検証可能な基準を書けない観点は「該当なし（理由）」でよい）を書いて残す。**受け入れ基準は適用範囲を明示して書く**（「すべてのエラーメッセージが日本語」ではなく「通常操作で出るエラーメッセージが日本語」— 全称の基準は環境側の失敗経路まで含み、検証で合格を示せなくなる）（後工程の受け入れ検証・非機能横断チェックが照合する）。前提・制約の「なし」に理由は不要。イテレーションの差分更新では**既存 NR の ID を維持**し、不足する観点の行を追記する（横断チェックは「観点」列で照合する）
4. **要件の追加・削除・変更を反映する場合**（開発中の要件変更・提案の採用・矛盾対応など、hearing を経由しない経路）: `docs/hearing-notes.md` の該当節（MVP スコープ・欲しい機能等）も同じ変更で更新する（ノートが陳腐化すると下記の漏れチェックが削除済み要件を復活させてしまう）

## セルフ整合性チェック

スキルの `playbooks/checklist-requirements.md` を使ってレビューする。

- **サブエージェントが使える場合**: fresh context のレビュアーに「`docs/requirements.md` の全文」と「チェックリスト全文」**のみ**を渡し、指摘リストを返させる（作成者バイアスの排除。ヒアリングの経緯は渡さない）。**2周目以降は前回の指摘リストと修正差分も併せて渡す**（同一指摘の再発見を防ぐ）
- **差分更新のとき**（修正依頼・要件変更・イテレーション・改変検知の再ゲート。承認前後を問わない）は、渡すものは初回と同じ**全文＋チェックリスト**に「変更点の要約」を添え、レビュアーへの指示で**指摘の対象を限定する**: 「指摘は**変更部分に起因するもの**（変更部分自体の欠陥、および**変更部分と既存本文との衝突**〔用語・トレーサビリティ・受け入れ基準の重複・矛盾〕）に限る。**未変更の本文だけに閉じた指摘は出さない**」。理由: 全文を無条件に見せると人間が既に承認した本文への指摘が周ごとに出続け、ゲート提示に「N 件未反映」が付いて人間が判断できなくなる（実地で 3周34件）。逆に入力を変更部分だけに絞ると、承認済み本文との矛盾を誰も検査しないまま承認に進む
- **使えない場合**: 自分でチェックリストを1項目ずつ適用する。修正したい衝動を抑え、まず指摘をすべて列挙する

指摘は `docs/log.md` に `finding` として記録**してから**修正する。**修正した指摘には対応記録「修正済み」、反映せず残した指摘には「ゲートで開示」を追記する**（周ごとに1エントリでよいが、`関連:` に各 finding の見出しを逐語で列挙する。対応記録が無いと、05 Step 1 の初回タスク化と整合性監査が未処理の指摘として拾う）。修正後に再チェックし、PASS するまで反復（最大3周。3周で収束しなければ残指摘を承認ゲートで人間に開示する）。各周の開始・完了を trail に `report` で記録し、再開時はそこから周回数を数える（完了の無い開始はその周をやり直す。起算点は直近の修正依頼 `interrupt` または承認リセットのエントリ — ゲートから戻るたびに 0 から）。

**セルフ整合性チェック終了後（PASS またはキャップ到達）の漏れチェック（作成者担当・双方向）**: レビュアーはヒアリングノートを渡されないため、**(1) ノートにあって要件に無いもの（拾い漏れ）と (2) 要件にあってノートにも trail にも出所が無いもの（作成者が独断で足したもの）の両方**を照合する。(2) が見つかったら、削除するか「提案」として出所を明示して hearing-notes に追記し、ゲートで提案由来として開示する（黙って承認させない）。以下、 レビュアーにはヒアリングノートを渡さないため、チェックリスト §4 の「漏れ」だけは作成者自身が `docs/hearing-notes.md` と要件を突き合わせて実施する。ノートにあって要件に無い事項が見つかれば反映する。**ただし log.md に意図的な削除・変更として記録されている事項、および hearing-notes の非ゴール節に載っている事項は「漏れ」とみなさない**（削除済み要件・コンセプト採用で置き換えられた要望を復活させない）。
漏れを反映した場合は、追加分が曖昧さ・テスト可能性の検査を通っていないため、**セルフ整合性チェックをもう1周**実行してからゲートへ進む（この1周は3周キャップの外。開始エントリに「漏れチェック後の追加周」と付記して再開時に区別する。FAIL なら指摘を修正し、なお残る指摘はゲートで開示して先へ進む — さらに周回しない）。

## 承認ゲート（唯一のブロッキングポイント）

1. SKILL.md Step 6 を実行（次 phase: `awaiting_approval`）。**ゲート提示前に必ずこの遷移を行う**（ここでセッションが切れても要件執筆をやり直さないため）
2. このときの報告がゲート提示を兼ねる。要件の要約（背景・MVP機能・非ゴール・成功基準を10行以内）に続けて、**非機能要件と前提・制約の各行を平たい言葉で1行ずつ**（例: 運用「失敗しても通知は来ません。朝見て無ければ失敗です」、費用「月 300 円まで」。提案由来の既定値はその旨を付ける）、`docs/requirements.md` の場所を提示し、AskUserQuestion で「承認する / 修正を依頼する / 質問がある」を提示して承認を求める（**UX ウォークスルー由来の要件追加案を含む提示では、選択肢を「追加案を採用して承認 / 追加案を見送って承認 / 修正を依頼する / 質問がある」にする**。見送りが選ばれたら追加案を requirements.md から外し、**外した版を人間に1行で示してから**承認としてハッシュする〔提示していない版をハッシュしない〕。**採否いずれでも元の finding に対応記録を付ける**（採用なら「修正済み」、見送りなら「最終報告で開示」））（**修正・質問が本文無しで選ばれたら、1回だけ「まとめて送ってください」と聞き、その事実を `interrupt` として記録して対応記録「本文待ち」を追記する** — 次の起動メッセージの扱いは「承認待ちからの再開」の本文待ちの規則に従う）。2回目以降の提示（修正依頼・要件変更・矛盾対応・改変検知・イテレーション）は先頭に「変更点: <前 → 後>」を必ず書く。提示には「修正したい点はそのまま返信に書いてください」と「※『進めて』『続きから』では先に進みません」を添える。内容が前回と同じ再掲なら先頭に「前回と同じ内容です」と書く。**提案由来の要件があれば要約で明示する**（ユーザーが自分の要求と提案を区別して承認できるように）

## 承認の判定と記録

- **承認・質問・曖昧な返事・停止・状況確認・不具合報告のいずれでもない内容は、すべて修正依頼として扱う**（不具合報告は要件を変えないので「人間の入力の経路」の表に従い、対応記録を付けずに残して 05 の整合に渡す）（「保存は JSON ファイルでいい」のような仕様・設計レベルの希望も含む。要件本文に該当が無ければ requirements.md の「前提・制約」に制約として書き、変更点を添えてゲートを再提示する — ここで記録しないと、承認後は凍結され下流のフェーズに届かない）
- **未反映の修正依頼がある間は承認を受理しない**（inbox に「修正依頼」と「承認」が続けて届いた場合など）。先に修正を反映してゲートを再提示し、そこから改めて判定する
- **要件への言及を伴う明示的な同意のみ**を承認とみなす（「承認」「承認します」「要件 OK です」「approved」等）
- **過去の版を指す同意は確認する**: 「さっきのは承認します」「前の版で OK」のように**どの版への同意か曖昧な言い方**は、そのまま承認にせず「いま提示している版（変更点: …）でよろしいですか」と1回だけ確認する（対応記録「再確認中」）
- **承認の時点を検査する**: 承認として扱えるのは、**phase が `awaiting_approval` であり、かつ現在のゲート提示（直近の `requirements -> awaiting_approval` 遷移）より後**に記録された発言だけ（`requirements` 中に届いた承認は、まだ提示していない版への同意なので下の「要件定義中の再開」で扱う）。それより前の同意（例: 修正依頼を出した後、修正版を提示する前に届いた「さっきのは承認します」）は、人間が**現在の版を読んでいない**ため承認にしてはならない。対応記録「後続指示により陳腐化」を追記し、ゲートを再提示する（判定は **log.md 上のエントリの並び**で行う〔追記専用なので位置が順序の正。inbox 経由の項目は転記した時点で末尾に追記される〕。時刻の文字列では判定しない）
- **修正を伴う返事は修正依頼として扱う**: 「承認します。ただし X を直して」のように同意と修正が混在する場合、承認とは記録**せず**「修正依頼の場合」の手順に従う（修正反映後にゲートを再提示する）
- **再開・進行の常套句は承認ではない**: 「続きから」「開発を進めて」「進めて」はセッション再開のトリガー語であり、要件を読んだ同意の証拠にならない。これらが来た場合は承認と記録せず、**先頭に「『進めて』は承認としては受け取っていません（要件を読んだうえでの同意が必要なためです）。内容がよければ「承認する」を選ぶか『承認します』と返信してください。直したい点があればそのまま書いてください」の1行を置いて**ゲートを再提示する（黙って同じ画面を返さない）
- 曖昧な返事（「うーん、たぶんいいよ」等）は承認とみなさず、「承認と受け取ってよいですか」と **AskUserQuestion（承認する / 修正を依頼する / 質問がある）**で再確認する（本文無しで選ばれたときの扱いはゲート提示と同じ）（曖昧な返事を trail に `interrupt` として記録し、対応記録「再確認中」を追記する。再確認への肯定〔はい・OK 等。再開語は除く〕は承認とみなし、確定したら対応記録「回答として処理」を追記する）
- **質問が来た場合**: `interrupt` として記録してから回答し、ゲートを再提示する（phase は `awaiting_approval` のまま）。回答したら対応記録「質問に回答済み」を追記する
- **承認されたら**: SKILL.md 共通手順「状態更新」の種別**「承認」**を実行する（承認の記録 → requirements.md の承認記録節 → sha256 → state.json → `specification` への遷移。途中で切れても Step 4 冒頭の復旧が同じ手順をやり直す）。遷移の報告で**「ここから先は自動で進めます。仕様化→設計→開発を続けて実行し、進捗は報告します」と宣言し、続けて「数十分〜数時間かかります。作業3件ごとに途中経過をお送りします。それより長く何も届かなければ止まっています（異常ではなく、作業は保存されています）。そのときは『進めて』と送ってください」と添えて、そのまま続行する**

## 修正依頼の場合

1. **まずユーザーの指摘内容を log.md に `interrupt` として記録する**（ここでセッションが切れても指摘が失われないように。再開で既に記録済みなら再記録は不要）
2. SKILL.md Step 6 で phase を `requirements` に戻す（**既に `requirements` なら実行しない** — 同じ phase への遷移は作らない）
3. 指摘を反映（差分更新）し、当該 interrupt への対応記録（修正済み）を追記 → セルフ整合性チェックを再実行 → ゲートを再提示（依頼に具体値が無ければ推測で置き、変更点で明示する）。承認されるまで先へ進まない

## 要件定義中の再開（phase が `requirements` で起動したとき）

執筆・修正の途中でセッションが切れた場合。起動メッセージの内容で分岐する（**この phase では承認を受理しない** — 人間はまだ現在の版を見ていない）:

- **承認の言葉**（「承認します」「さっきので OK」）→ `interrupt` として記録し、対応記録「後続指示により陳腐化」を追記して、執筆・修正を続けてからゲートを提示する（提示時に「反映後の版で改めて確認をお願いします」と一言添える）
- **修正依頼・要件変更** → 「修正依頼の場合」の手順3から続ける（phase は既に `requirements` なので Step 6 は実行しない）
- **質問** → `interrupt` として記録して回答し、対応記録「質問に回答済み」を追記してから執筆・修正を続ける
- **曖昧な返事**（「うーん、たぶんいいよ」等）→ 承認としても修正依頼としても扱わず、`interrupt` として記録して執筆・修正を続け、完成後のゲート提示で改めて確認する
- **単なる再開語** → 書きかけの成果物と log.md の**未反映の修正依頼および対応記録の無い要件矛盾の `finding`**（03/04 から承認リセットで戻された場合）を確認し、反映して続きから完成させる

いずれの場合も、完成したらセルフ整合性チェック → 承認ゲートまで同一ターンで進む。

## 承認待ちからの再開（phase が `awaiting_approval` で起動したとき）

このターンを起動したユーザーメッセージを「承認の判定と記録」節で**判定することから始める**（**停止指示と状況確認だけは先に reporting.md の割り込み手順で処理する** — 承認判定にかけない）（判定の前にゲートを再提示して往復を浪費しない。判定の結果として必要な再提示は行う）:

- trail の直近の対応記録が**「本文待ち」**なら、起動メッセージを**先に「承認の判定と記録」にかけ**（「やっぱり承認します」なら承認、「はい、X を直して」は修正を伴う返事なので修正依頼）、どちらでもなければ修正内容・質問の**本文**として扱う。**本文とみなす範囲は reporting.md の語彙定義に従う** — 再開語だけのメッセージは本文でも承認でもないので、同じ聞き返しを再提示して待つ
- trail の直近の対応記録が**「再確認中」**（承認かどうかを聞き返した状態）で起動メッセージが肯定（再開語を除く）なら承認として扱う（**修正を伴う肯定**〔「はい、でも X を直して」〕は上の「修正を伴う返事は修正依頼として扱う」を優先する）
- `approval.approved` が false で起動メッセージが再開語の場合: log.md の直近に**未反映の修正依頼**が記録されていれば、ゲート再提示ではなく「修正依頼の場合」の手順から再開する
- **承認手続きの途中で切れていた場合**は、Step 4 冒頭の復旧（共通手順「状態更新」）が承認を完了させて `specification` に進めている。起動メッセージはその後、自律区間の入力として「人間の入力の経路」の表で扱う（修正依頼・要件変更なら承認リセット、停止なら停止）
