# Phase: 要件定義

**入力**: `docs/hearing-notes.md`
**成果物**: `docs/requirements.md`（`templates/requirements.md` に従う）
**このフェーズの最後に、ワークフロー唯一のブロッキングポイントである承認ゲートがある。**

## 執筆

1. `templates/requirements.md` をコピーして雛形にする
2. ヒアリングノートの内容を要件に落とす:
   - 機能要件は必ず ID (R-1, R-2, ...) と受け入れ基準を付ける
   - 受け入れ基準は検証可能な形（誰が読んでも合否判定できる）で書く
   - 非ゴール節は必須。ヒアリングで合意した内容をそのまま書く
   - ユーザーの言葉と要件の対応が取れるようにする（勝手な機能追加をしない）

## セルフ整合性チェック

`checklist-requirements.md` を使ってレビューする。

- **サブエージェント（Task ツール等）が使える場合**: fresh context のレビュアーに「`docs/requirements.md` の全文」と「チェックリスト全文」**のみ**を渡し、チェックリストに従った指摘リストを返させる（作成者バイアスの排除）。ヒアリングの経緯は渡さない
- **使えない場合**: 自分でチェックリストを1項目ずつ適用する。修正したい衝動を抑え、まず指摘をすべて列挙する

指摘は `docs/log.md` に記録**してから**修正する。修正後に再チェックし、PASS するまで反復（最大3周。3周で収束しなければ残指摘を承認ゲートで人間に開示する）。

## 承認ゲート（唯一のブロッキングポイント）

1. 要件の要約（背景・MVP機能・非ゴール・成功基準を10行以内）と `docs/requirements.md` の場所を提示する
2. 承認を求める:
   - **nanoclaw**: 「内容が良ければ『承認』と返信してください。修正点があればそのまま指摘してください」と送り、`phase` を `awaiting_approval` にしてターン終了
   - **Claude Code**: AskUserQuestion で「承認する / 修正を依頼する / 質問がある」を提示

## 承認の判定と記録

- **明確な同意のみ**を承認とみなす（「承認」「OK、進めて」「approved」等）
- 曖昧な返事（「うーん、たぶんいいよ」「まあいいんじゃない」等）は承認とみなさず、「承認と受け取ってよいですか」と再確認する
- 承認されたら:
  1. `docs/requirements.md` の承認記録節を埋める
  2. sha256 を計算（`shasum -a 256 docs/requirements.md`）
  3. `docs/hotl.state.json` の `approval` を埋める: `approved: true`、`approved_by`（ユーザー名または "user"）、`approved_at`、`runtime`、`document_sha256`、git commit hash
  4. log.md に承認を記録し、git commit
  5. `phase` を `specification` へ。**「ここから先は自律区間です。仕様化→設計→開発を続けて実行し、進捗は報告します」と宣言して、そのまま続行する**

## 修正依頼の場合

指摘を反映 → セルフ整合性チェックを再実行 → ゲートを再提示。承認されるまで先へ進まない。
