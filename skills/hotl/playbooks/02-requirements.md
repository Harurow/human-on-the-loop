# Phase: 要件定義

**入力**: `docs/hearing-notes.md`
**成果物**: `docs/requirements.md`（スキルの `templates/requirements.md` に従う）
**このフェーズの最後に、ワークフロー唯一のブロッキングポイントである承認ゲートがある。**

## 執筆

1. `docs/requirements.md` が**既に存在する場合**（修正依頼・イテレーション・再開）は再生成せず、変更点だけの差分更新にする。初回のみ、スキルの `templates/requirements.md` をコピーして雛形にする。既存ファイルにガイドコメントや未記入の `<...>` が残っていれば前回の書きかけなので、差分更新ではなく未完成部分を埋めて完成させる
2. ヒアリングノートの内容を要件に落とす:
   - 機能要件は必ず ID (R-1, R-2, ...) と受け入れ基準を付ける
   - 受け入れ基準は検証可能な形（誰が読んでも合否判定できる）で書く
   - 非ゴール節は必須。ヒアリングで合意した内容をそのまま書く
   - 各機能要件に**出所**（ユーザー / 提案）を記す。ヒアリングで**採用された**エージェント提案、または trail の `proposal` に採用が記録された提案のみ「提案」として要件化する（勝手な機能追加をしない）
3. **非機能要件の必須5観点**（性能目標・費用上限・セキュリティ前提・データ保全・運用）と**前提・制約**（実行環境・既存資産・外部サービス）を必ず埋める。ヒアリングノートに値が無ければ**質問で往復せず**、合理的な既定値を置いて出所を「提案」にし、承認ゲートの要約で「提案由来」として明示して確認を受ける。既定値の例: 費用上限は「想定実行頻度 × 1実行あたりの想定単価」の概算の1.5倍、想定実行頻度は採用コンセプトの形態から〔定期実行なら1日 n 回・対話型なら1日あたりの想定操作回数〕、想定データ量は利用シーンから概算、公開範囲はローカルのみ、データ保全は「ローカル保存のみ・消失許容」、運用は「失敗は次回実行時の標準出力で判明」、前提・制約は「なし」。非機能の「なし」行にも理由と受け入れ基準（検証可能な基準を書けない観点は「該当なし（理由）」でよい）を書いて残す（後工程の受け入れ検証・非機能横断チェックが照合する）。前提・制約の「なし」に理由は不要。イテレーションの差分更新では**既存 NR の ID を維持**し、不足する観点の行を追記する（横断チェックは「観点」列で照合する）
4. **要件の追加・削除・変更を反映する場合**（開発中の要件変更・提案の採用・矛盾対応など、hearing を経由しない経路）: `docs/hearing-notes.md` の該当節（MVP スコープ・欲しい機能等）も同じ変更で更新する（ノートが陳腐化すると下記の漏れチェックが削除済み要件を復活させてしまう）

## セルフ整合性チェック

スキルの `playbooks/checklist-requirements.md` を使ってレビューする。

- **サブエージェントが使える場合**: fresh context のレビュアーに「`docs/requirements.md` の全文」と「チェックリスト全文」**のみ**を渡し、指摘リストを返させる（作成者バイアスの排除。ヒアリングの経緯は渡さない）。**2周目以降は前回の指摘リストと修正差分も併せて渡す**（同一指摘の再発見を防ぐ）
- **使えない場合**: 自分でチェックリストを1項目ずつ適用する。修正したい衝動を抑え、まず指摘をすべて列挙する

指摘は `docs/log.md` に記録**してから**修正する。修正後に再チェックし、PASS するまで反復（最大3周。3周で収束しなければ残指摘を承認ゲートで人間に開示する）。各周の開始・完了を trail に `report` で記録し、再開時はそこから周回数を数える（完了の無い開始はその周をやり直す。起算点は直近の修正依頼 `interrupt` または承認リセットのエントリ — ゲートから戻るたびに 0 から）。

**PASS 後の漏れチェック（作成者担当）**: レビュアーにはヒアリングノートを渡さないため、チェックリスト §4 の「漏れ」だけは作成者自身が `docs/hearing-notes.md` と要件を突き合わせて実施する。ノートにあって要件に無い事項が見つかれば反映する。**ただし log.md に意図的な削除・変更として記録されている事項、および hearing-notes の非ゴール節に載っている事項は「漏れ」とみなさない**（削除済み要件・コンセプト採用で置き換えられた要望を復活させない）。
漏れを反映した場合は、追加分が曖昧さ・テスト可能性の検査を通っていないため、**セルフ整合性チェックをもう1周**実行してからゲートへ進む（この1周は3周キャップの外。開始エントリに「漏れチェック後の追加周」と付記して再開時に区別する。FAIL なら指摘を修正し、なお残る指摘はゲートで開示して先へ進む — さらに周回しない）。

## 承認ゲート（唯一のブロッキングポイント）

1. SKILL.md Step 6 を実行（次 phase: `awaiting_approval`）。**ゲート提示前に必ずこの遷移を行う**（ここでセッションが切れても要件執筆をやり直さないため）
2. このときの報告がゲート提示を兼ねる。要件の要約（背景・MVP機能・非ゴール・成功基準を10行以内）に続けて、**非機能要件と前提・制約の各行を平たい言葉で1行ずつ**（例: 運用「失敗しても通知は来ません。朝見て無ければ失敗です」、費用「月 300 円まで」。提案由来の既定値はその旨を付ける）、`docs/requirements.md` の場所を提示し、AskUserQuestion で「承認する / 修正を依頼する / 質問がある」を提示して承認を求める。2回目以降の提示（修正依頼・要件変更・矛盾対応・改変検知・イテレーション）は先頭に「変更点: <前 → 後>」を必ず書く。提示には「修正したい点はそのまま返信に書いてください」を添える。選択肢だけが選ばれたら1回だけ「直したい点（または質問）をまとめて送ってください」と聞く。内容が前回と同じ再掲なら先頭に「前回と同じ内容です」と書く。**提案由来の要件があれば要約で明示する**（ユーザーが自分の要求と提案を区別して承認できるように）

## 承認の判定と記録

- **要件への言及を伴う明示的な同意のみ**を承認とみなす（「承認」「承認します」「要件 OK です」「approved」等）
- **修正を伴う返事は修正依頼として扱う**: 「承認します。ただし X を直して」のように同意と修正が混在する場合、承認とは記録**せず**「修正依頼の場合」の手順に従う（修正反映後にゲートを再提示する）
- **再開・進行の常套句は承認ではない**: 「続きから」「開発を進めて」「進めて」はセッション再開のトリガー語であり、要件を読んだ同意の証拠にならない。これらが来た場合は承認と記録せず、ゲートを再提示する
- 曖昧な返事（「うーん、たぶんいいよ」等）は承認とみなさず、「承認と受け取ってよいですか」と再確認する（再確認を出した事実を trail に `interrupt`〔対応: 再確認中〕として記録する。この再確認への肯定は承認とみなす）
- **質問が来た場合**: 回答し、ゲートを再提示する（phase は `awaiting_approval` のまま）
- **承認されたら**（順序厳守。途中でセッションが切れても「承認待ちからの再開」で続きから完了できる）:
  1. log.md に承認を `approval` として記録する（**処理の前に**。承認者と発言の要旨）
  2. `docs/requirements.md` の承認記録節に**承認者と日時（`date +"%Y-%m-%dT%H:%M:%S%z"`）のみ**記入する。**これ以降、requirements.md には一切書き込まない**（ハッシュの対象となる最終状態を確定させるため）
  3. sha256 を計算: `shasum -a 256 docs/requirements.md | cut -d' ' -f1`（`shasum` が無い環境は `sha256sum`。先頭フィールドがハッシュ）
  4. `docs/hotl.state.json` の `approval` を埋める: `approved: true`、`approved_by`（発言者名。不明なら "user"）、`approved_at`、`document_sha256`
  5. SKILL.md Step 6 を実行（次 phase: `specification`）。報告で**「ここから先は自動で進めます。仕様化→設計→開発を続けて実行し、進捗は報告します」と宣言して、そのまま続行する**

## 修正依頼の場合

1. **まずユーザーの指摘内容を log.md に `interrupt` として記録する**（ここでセッションが切れても指摘が失われないように。再開で既に記録済みなら再記録は不要）
2. SKILL.md Step 6 で phase を `requirements` に戻す
3. 指摘を反映（差分更新）し、当該 interrupt への対応記録（修正済み）を追記 → セルフ整合性チェックを再実行 → ゲートを再提示（依頼に具体値が無ければ推測で置き、変更点で明示する）。承認されるまで先へ進まない

## 承認待ちからの再開（phase が `awaiting_approval` で起動したとき）

このターンを起動したユーザーメッセージを「承認の判定と記録」節で**判定することから始める**（判定の前にゲートを再提示して往復を浪費しない。判定の結果として必要な再提示は行う）:

- trail の直近が「再確認中」で起動メッセージが肯定なら承認として扱う
- `approval.approved` が false で起動メッセージが再開語の場合: log.md の直近に**未反映の修正依頼**が記録されていれば、ゲート再提示ではなく「修正依頼の場合」の手順から再開する
- **承認手続きの途中中断**（`approval.approved` が既に true、または false でも log.md 末尾に state 未反映の**承認**の `approval` エントリがある — 承認リセットのエントリは含めない）: **まず起動メッセージの内容を確認**し、修正依頼・要件変更なら承認リセットで、停止指示なら停止で応じる。単なる再開・継続の意図なら再判定せず、「承認されたら」の未実施手順を続きから完了させる（承認記録節が記入済みなら手順3から。`approved` が true なら Step 6 遷移のみ）
