# HOTL Orchestrator

このスキルはステートマシンである。プロジェクトの state ファイルを読み、現在フェーズの playbook を Read して実行する。
承認ゲート（要件承認）以降は人間をブロックせず自律的に開発を完走する。

**パス規約**: `playbooks/...` `templates/...` は、この SKILL.md と同じディレクトリ（スキルディレクトリ）からの相対パス。成果物（`docs/...`）はターゲットプロジェクトルートからの相対パス（一覧は state.json の `artifacts` に列挙）。**Step 2 でプロジェクトを特定したら、以後のコマンド・相対パスはすべてプロジェクトルートを cwd として実行する**。cwd が呼び出しごとに戻る環境（サブエージェントでの委譲実行など）では、`cd <プロジェクトルートの絶対パス> && ...` または `git -C <絶対パス>` の形で実行する。**`git log` の結果を判定に使う前に `git rev-parse --show-toplevel` がプロジェクトルート（`repo` が `"parent"` なら親）であることを確かめる** — 別ディレクトリで実行した `git log` は空を返し、エラーにならないまま「履歴なし」と誤判定される。

**時刻**: タイムスタンプは必ず `date` コマンドの実行結果を使い、推測で書かない。state.json は `date +"%Y-%m-%dT%H:%M:%S%z"`（ISO8601）、log.md の見出しは `date +"%Y-%m-%d %H:%M"`。

**テンプレート**: `templates/` をコピーして成果物を作る際は、`<!-- ... -->` の記入ガイドコメントをすべて削除してから記入する（成果物にガイド文を残さない。レビュー・ハッシュの対象は記入済み本文のみにする）。

**ID 規約**: R-n / NR-n / S-n / T-n / L-n の ID は永続とする。項目を削除しても欠番のまま残し、**番号を振り直さない**（振り直すとトレーサビリティが壊れる）。

## エージェント構成とコンテキスト分離

原則: **フェーズ間の受け渡しは docs/ の成果物ドキュメントのみ**。会話履歴を下流フェーズに持ち込まない。レビュー・検証は必ず作成者と別コンテキストで行う。

| 役割 | 実行場所 |
|---|---|
| オーケストレーション・報告・承認ゲート | メインループ |
| ヒアリング・要件執筆 | メインループ |
| 要件レビュー | サブエージェント（fresh context） |
| 仕様化 / 設計 | サブエージェント（各1体） |
| 実装ループ | メインループ |
| コードレビュー（タスク毎） | サブエージェント（fresh context） |
| 整合性監査・UX ウォークスルー・最終受け入れ検証・セキュリティレビュー（done 前） | サブエージェント（fresh context、それぞれ別の1体） |

各役割に**渡す入力は、その役割を呼び出す playbook の記述が唯一の正**（ここに重複して書かない）。例外: 非機能横断チェックの費用算出（05 (c)）はメインループが行う（機械的な計算で作成者バイアスが問題にならない）。

- **モデル方針**: サブエージェントのモデルは明示指定せず、セッションモデルを継承する（既定）。理由: (1) 役割ごとのモデル選定ミスで品質の底が抜けるのを防ぐ、(2) コストと品質の調整はユーザーがセッションモデルの選択で一元的に行える。**モデル自体のダウングレード・effort の引き下げはレビュー・検証・監査役には行わない**（検出力が下がる）
- サブエージェント（Task / Agent ツール）が使えない環境では、**同じ入力制約を守って**インラインで代替する

**「渡す」の意味**: 原則として**内容をプロンプトに直接載せる**（インライン）。大きすぎる場合はファイルの絶対パスを渡し、**「このファイルだけを Read してよい。他のファイル・リポジトリの探索は禁止」**と明示する（パスだけ渡して読ませ放題にしない）。**この制限は抜粋・単一ファイルを渡す役割**（仕様化・設計・コードレビュー・要件レビュー）**に適用する** — 入力自体が「リポジトリ」「docs/ 一式」である役割（セキュリティレビュー・整合性監査・受け入れ検証）は作業ツリー全体を読んでよい（`.gitignore` 対象の秘密情報を除く）。

**読み込み規律**:

- 各役割は自分の入力リストにあるものだけを読む。docs/ やリポジトリ全体を無条件に読み込まない
- trail・会話の内容は生ログではなく要約・末尾数件で渡す
- 過去イテレーションの資料・アーカイブは、現在のタスクに関係する場合のみ読む
- **個別の playbook が指定する入力リストは、この一般規律に優先する**（例: 整合性監査は docs/ 一式＝trail 全文を受け取る）

## 共通規則: 承認済み要件の凍結

`approval.approved` が true の間は `docs/requirements.md` を書き換えない（人間も機械も。変更はすべて承認リセット経由）。監査・レビューで requirements.md 側の不備（用語・参照の陳腐化等）が指摘されても修正せず、最終報告で開示するか、要件変更なら承認リセットで扱う。

## 共通手順: 人間の入力の経路

人間のメッセージ（ターンの起動メッセージ・実行中の割り込み・`docs/inbox.md` 経由のいずれも）は次の順で扱う:

1. **処理を始める前に trail に `interrupt` として記録する**（状況確認だけは記録しない）。秘密情報の値は伏せ字
2. **複数あれば最新の人間の意図が勝つ**（停止 → 再開など）。比較対象は**人間のメッセージのみ** — hotl-pm の委譲プロンプト（「続きから」等）は人間の発話ではない
3. 下の表で内容を判定し、phase に応じた処理先へ渡す。**表のどれにも当たらない内容（雑談・感想を除く指示）は「仕様・設計レベルの希望」の行として扱う**

| 内容 | 対話フェーズ（`hearing` / `requirements` / `awaiting_approval`） | 自律区間（`specification` / `design` / `development`） | `done` | 対応記録 |
|---|---|---|---|---|
| 停止指示 | reporting.md 割り込み手順1 の ⏸ で応答してターンを終える（phase を問わず同じ） | 同左 | 同左 | 停止済み |
| 状況確認 | 1〜2行で答えて**続行**（trail に記録しない。ターンの起動メッセージだった場合は Step 5 の状況確認クエリ） | 同左 | 同左 | — |
| 単純な質問 | 1〜2行で答えて**続行** | 同左 | 同左 | 質問に回答済み |
| 人間待ち（⛔ / 環境の確認）への回答 | 入力の実在を確認して再開 | 同左 | 同左 | 入力確認済み（確認できなければ 本文待ち） |
| ⚠️ キャップ超過への A/B/C/D の回答 | 起きない | 05「最終受け入れ検証」の手順4-3 へ渡す（**「入力確認済み」は付けない**） | 起きない | T-n として登録（B は 修正済み） |
| ゲート応答（承認・修正依頼・質問・曖昧な返事・本文無しの選択） | 各 playbook の再開節へ渡す（`hearing` → 01、`requirements` → 02「要件定義中の再開」、`awaiting_approval` → 02「**承認待ちからの再開**」〔本文待ち・再確認中・途中中断の分岐を含む〕） | 起きない | 起きない | 回答として処理 / 修正済み / 質問に回答済み |
| 仕様・設計レベルの希望 | `hearing` / `requirements`: hearing-notes に記録し要件化時に前提・制約へ。`awaiting_approval`: 02 へ渡し**修正依頼として** requirements.md の前提・制約に反映してゲート再提示 | reporting.md 割り込み手順2（該当ドキュメントを更新して続行） | 下のイテレーション | 反映済み |
| 要件レベルの変更（追加・削除・意味の変更） | `hearing` は 01 で取り込む。`requirements` / `awaiting_approval` は 02 の差分更新（`approved` が true なら承認リセット） | **承認リセット**（次 phase: `requirements`） | イテレーション（次 phase: `hearing`） | 修正済み |
| 新しい要望 | 01 / 02 で取り込む | 要件レベルの変更と同じ | **イテレーション**（次 phase: `hearing`） | イテレーション開始 |
| 不具合報告（承認済み基準の不合格） | `interrupt` のまま**対応記録を付けずに残す**（修正タスクの登録も検証タスクの再追記も 05 Step 1 のバックログ整合が行う。ここで先にタスクを挿入すると、整合が「追加するタスクは無い」と判断して検証タスクを再追記せず、修正が検証を受けないまま done に戻る） | `development` で tasks.md があれば、**その場で 05 Step 1 のバックログ整合を実行してから続行する**（再入可能。次の起動を待つと、同一ターンで done に到達したときに拾われない）。それ以外は同左 | 同左（承認リセットはせず Step 6 で `development` へ） | 05 の整合で T-n として登録 |
| 単純な再開語 | 各 playbook の再開節（`awaiting_approval` はゲート再提示） | そのまま続行 | 短い完了応答 | 再開 |

処理の詳細な手順・人間への文面は `playbooks/reporting.md`「割り込みへの対応」が正。この表は**どこへ渡すか**だけを定める。

## 共通手順: 承認リセット

承認済み要件を無効化する場面、または承認状態を信頼できない場面（要件変更・矛盾発見・改変検知・不変条件違反・イテレーション開始）では、必ず次の3点をセットで行う:

1. （Step 4 で控えたハッシュ不一致があれば、後退報告の理由に「要件定義書が承認後に変わっていた」を添える）**まず** 旧承認記録（承認者・日時・ハッシュ）を log.md に `approval` として退避し（**記録が先** — ここで切れても次のセッションが承認リセットの途中と判定できる）、**次に** state.json の `approval` を初期状態に戻す（`approved: false`、`approved_by` / `approved_at` / `document_sha256` を null）（**タイトルは `承認リセット（<種別>）` に固定する** — 承認エントリと機械的に区別できるように）（元々未承認なら退避内容は無いが、承認リセットの `approval` エントリ自体は必ず書く — 02 の周回起算点になる）
2. `docs/requirements.md` の承認記録節を「未承認」に戻す（これに伴い requirements.md への書き込み禁止も解除される）
3. Step 6 を実行して phase を戻す（要件変更・矛盾発見・改変検知〔`done` でも〕・不変条件違反 → `requirements`、イテレーション → `hearing`）

## Step 1: 準備

最初に `playbooks/reporting.md` を Read し、以後の報告・質問・承認の方法はすべてそれに従う。

## Step 2: プロジェクト特定

カレントディレクトリがプロジェクト。`docs/hotl.state.json` を探す。

- **ワークスペースガード**: cwd に state が無く、`.claude/skills/hotl-pm` が存在する、または直下のサブディレクトリに `*/docs/hotl.state.json` がある場合、cwd はプロジェクトではなく**ワークスペース**である。**cwd をブートストラップしてはならない**。`.claude/skills/hotl-pm` があれば **hotl-pm の Step 1 から実行し、以後の采配（対象の特定・委譲・報告の中継）は hotl-pm に従う**（同じ入力が hotl で始まるか hotl-pm で始まるかによって実行形態が変わらないようにするため）。hotl-pm がインストールされていない場合は、サブディレクトリのプロジェクト一覧を提示して対象を確認し（新規開発の意図なら、要望から kebab-case の仮名〔決められなければ `new-app-YYYYMMDD`〕でサブディレクトリを作る。同名のディレクトリを乗っ取らない）、特定されたプロジェクトをルートとして続行する（hotl-pm の導入を提案してよい）
- **不正状態の検査**: cwd に state が**有り**、かつ `.claude/skills/hotl-pm` も存在する場合、ワークスペース直下がプロジェクト化された不正状態である。作業せず人間に報告し、退避（サブディレクトリへの移動等）の指示を仰ぐ（推奨案を添えて AskUserQuestion で聞く）
- **state が見つからない場合**（ワークスペースでもない）:
  - 新規開発の意図が明確に読み取れる → Step 3 へ
  - 「続きから」「進捗を教えて」等で新規の意図が読み取れない → **ブートストラップしてはならない**。対象プロジェクトが見つからない旨を報告し、新規開発かどうかを確認する

## Step 3: ブートストラップ（state ファイルが無い場合のみ）

各手順は冪等（既にあるものは作り直さない。項目1の衝突確認のみ人間確認で分岐しうる）。**state.json は最後に生成する**（完了マーカー。途中でクラッシュしても state が無いので次回 Step 3 が残りを補う）:

1. プロジェクト直下に `docs/` を作成。**既に docs/ があり、`templates/state.json` の `artifacts` と同名のファイル（requirements.md / log.md 等）が存在する場合は上書き・追記してはならない**: hotl 管理外のファイルとして報告し、扱い（別名へ退避するか、hotl が既存内容を引き継ぐか）を推奨案付きの AskUserQuestion で確認する。**例外**: `docs/log.md` が存在し、項目4の開始エントリ（`## YYYY-MM-DD HH:MM [report] hotl 開始`。type とタイトルが完全一致）を含むなら、前回のブートストラップ中断で hotl 自身が作ったものとみなして引き継ぐ（追記のみ。管理外扱いにしない）
2. `git rev-parse --show-toplevel` がプロジェクトルートと一致しなければ `git init`（親ディレクトリが git 管理下でも各プロジェクトは独立リポジトリ。ただしプロジェクト内のファイルが親リポジトリで tracked 済み〔`git ls-files` に出る〕なら入れ子にせず、扱い（「このフォルダだけ独立して管理する（推奨）／親のリポジトリのまま使う」）を推奨案付きの AskUserQuestion で確認する。「親リポジトリのまま使う」なら state.json の `repo` を `"parent"` にし、以後は項目2の残りのうち **`git init` だけをスキップする**（コミット作者の設定確認は**親リポジトリに対して**行う — 未設定のままだと以後の commit がすべて失敗する）。commit は親リポジトリへ行う）。`git config user.name` / `git config user.email` を確認し、**未設定の側だけ**をリポジトリローカルに設定する（例: `hotl` / `hotl@localhost`。設定済みの側は上書きしない。これが無いと以後の全 commit が失敗する）
3. `.gitignore` が無ければ、スキルの `templates/gitignore` をコピーして作成する。**秘密情報（接続情報・API キー・トークン・パスワード）の値は .env 等の gitignore 対象ファイルにのみ置き、docs/・trail・コード・commit に書かない**（参照するときは名前と置き場所だけを書く）
4. `docs/log.md` が無ければ作成し、開始エントリを追記する: 見出しは `## YYYY-MM-DD HH:MM [report] hotl 開始`（type・タイトル固定。項目1の判定に使う）、本文に**ユーザーの初回要望の要旨を含める**（クラッシュしても要望が失われないように）
5. `templates/state.json` を元に `docs/hotl.state.json` を生成（`project`・各タイムスタンプ・`repo`〔項目2の決定。既定 `"own"`〕を埋める。`project` はプロジェクトのディレクトリ名。`phase` は `"hearing"`。`version` / `framework` はテンプレート値のまま）
6. Step 5 へ（hearing から開始）

## Step 4: 状態読み込みと整合性チェック

`docs/hotl.state.json` を Read し、次を順に確認する（**状況確認クエリ**〔Step 5〕の場合は inbox を読むだけで転記・反映せず、環境の自己修復も行わず、以下の検査で異常を検知しても state を変更しない — 報告に留める）:

- **環境の自己修復**（人間確認が要る場合、その回答が起動メッセージや inbox にあればそれを使い、再質問しない）: `docs/log.md` が無い、git のトップレベルがプロジェクトルートでない（`repo` が `"parent"` なら対象外）、または `.gitignore` が無い場合は、Step 3 の該当手順を補ってから続ける（各手順は冪等）。（**既存の log.md を引き継ぐ場合は開始エントリを足さない** — 開始エントリは初回ブートストラップの1回だけ）。ただし log.md をブートストラップ後に再生成する場合の先頭エントリは `[report] log.md 再生成（自己修復）` とし、本文に現在の phase と直近の成果物の要約を書く（「hotl 開始」は使わない）
- **文脈復元**: 続けて `docs/log.md` の末尾（直近のエントリ数件）を Read し、直近の報告・指摘・判断を把握する。**`phase_history` の末尾エントリに対応する遷移報告が log.md に無ければ**（Step 6 の手順1と2の間で切れた場合。**ブートストラップ直後の最初のエントリ〔`hearing`〕は遷移ではないので対象外**）、遷移報告を補って記録してから進む（自己修復。人間への再送はしない）。**修正依頼の内容や要件変更の差分は log.md の記録を正とする**（再開したセッションはこれ無しに「差分なし」と判断してはならない）。`docs/lessons.md` があれば併せて確認し、封印済みの方法を避ける（フェーズを問わず適用）
- **承認済みハッシュの照合（読み取りのみ）**: `approval.approved` が true なら `shasum -a 256 docs/requirements.md | cut -d' ' -f1`（`shasum` が無い環境は `sha256sum`。先頭フィールドがハッシュ）で現在値を計算し `approval.document_sha256` と比較して、結果を控える（inbox の消化で承認リセットが先に走っても改変の事実を開示できるように）
- **inbox の消化**: `docs/inbox.md`（hotl-pm が人間の指示を届ける受け渡しファイル）が存在し内容があれば、フェーズ実行の**前に**次を行う:
  - **読んだ項目だけ**を trail に `interrupt` として転記して inbox から削除する（読取後に追記された新項目を消さない）。複数あればまとめて読み、**1項目ずつ「転記 → その項目を削除」**を繰り返す（転記後・削除前のクラッシュで二重転記しないため。再開時は、同じ見出し〔時刻〕と本文の `interrupt` が trail に既にあれば転記せず削除だけ行う）
  - 分類と処理先は**共通手順「人間の入力の経路」**に従う（記録は転記済みなので、同手順の記録ステップは省いて分類から適用する。二重記録しない）
  - 転記と同時に対応記録を追記する: 単純な再開指示（「進めて」等）には「対応: 再開」、後続の指示に上書きされた項目には「対応: 後続指示により陳腐化」（監査の未処理判定に残さない）
  - trail 末尾に**対応記録の無い interrupt** が残っている場合も同様に、フェーズ実行の前に同じ経路で処理する（記録済みなので分類から。直後に承認リセット〔イテレーション〕の記録があれば、**phase が既に `hearing` に戻っているときに限り**対応記録「イテレーション開始」を補うだけにし〔`done` のままなら承認リセットの手順3〔Step 6〕から続ける〕、直後に `done -> development` の遷移記録があれば 05 Step 1 の整合に委ねる。単純再開と誤判定して旧方針のまま進まない）

- **承認済みハッシュの照合**（**inbox に停止指示があった場合は、停止の応答を優先してターンを終える** — 改変の事実は次回起動時に同じ照合で開示される）: 先行して控えた結果を使う（再計算しない。inbox 消化で既に承認リセットしたなら本項目は行わない — 開示は共通手順の手順1で済んでいる）。**不一致なら自律続行してはならない**: 「承認後に要件定義書が変わっていた」ことを diff の要旨・想定原因（整形ツール・手編集等）・「内容が同じなら再度の承認で続行できます（完了後で、かつ成果物に変更が入る場合は最終検証〔監査・受け入れ・セキュリティ等〕をやり直します）」を添えて報告し（整形ツール由来と判明しても扱いは同じ — ハッシュが正。除外設定の不備は tasks.md があれば reporting.md ②の位置に登録し、無ければ `finding` として記録して 05 Step 1 の初回生成でタスク化する）、**承認リセット**（次 phase: `requirements`。`done` でも同じ — 新しい要望が無いのでヒアリングに戻さない。新しい要望を伴う場合は本項目を実行せず下の「イテレーション」項目に従う。**不具合報告を伴う場合**は本項目の承認リセットを行った上で、その不具合を `interrupt` として記録しておく — 再承認後の 05 Step 1 のバックログ整合が修正タスクと検証タスクを追加する）を行って承認ゲートを再実行する
- **自律区間の不変条件**: `phase` が `specification` / `design` / `development` なのに `approval.approved` が true でないのは不正状態（承認前に自律区間へ入っている）。**承認リセット**（次 phase: `requirements`）でゲートからやり直す
- **`done` の不変条件**: `phase` が `done` なのに `approval.approved` が false なのは、承認リセットの記録だけが済んで phase 遷移が済んでいない状態（途中クラッシュ）。**承認リセットは既に記録済みなので繰り返さず**、log.md 直近の承認リセットの種別に従って Step 6 だけを実行する（イテレーション → `hearing`、それ以外 → `requirements`）
- **イテレーション**: `phase` が `done` のプロジェクトに新しい要望が来たら、**まず要望の内容を trail に `interrupt` として記録し**（処理前に。クラッシュで失わないため。対応記録「対応: イテレーション開始」は承認リセットの遷移後に追記する）、**承認リセット**（次 phase: `hearing`）で差分ヒアリングから同じ流れを回す。改変検知と同時なら本項目を優先する（控えた不一致は承認リセット手順1で開示される）。**イテレーションでは各フェーズとも既存成果物の差分更新**として実行する（テンプレートからの再生成をしない）。ただし**承認済みの受け入れ基準に対する不具合の報告**（「◯◯が動かない」）は要望ではない: `interrupt` として記録した上で承認リセットせず Step 6 で `development` に戻し、05 Step 1 のバックログ整合で修正タスクと検証タスクを追加する

## Step 5: フェーズ実行

**状況確認クエリの場合**（「進捗を教えて」等、作業の続行を求めていない質問）: playbook を実行せず、state・log.md・（あれば）tasks.md を基に現状を報告してターンを終える。

それ以外は `phase` に対応する playbook を Read して、その内容に従って実行する（自律区間の再開なら、その直前に reporting.md「再開時の一言」を出す）:

| state.phase | playbook |
|---|---|
| hearing | `playbooks/01-hearing.md` |
| requirements | `playbooks/02-requirements.md` |
| awaiting_approval | `playbooks/02-requirements.md` — 02「承認待ちからの再開」節から始める（起動メッセージの判定が先。ゲートの無条件再提示をしない） |
| specification | `playbooks/03-specification.md` |
| design | `playbooks/04-design.md` |
| development | `playbooks/05-development.md` |
| done | 「完了しています。新しい要望があればどうぞ」の短い応答のみ（最終報告を再送しない）。新しい要望があれば Step 4 のイテレーション開始。**log.md の直近に未処理の新要望（interrupt）が残っている場合**（記録直後にクラッシュした再開）も、完了報告ではなくイテレーション開始から再開する |

## Step 6: フェーズ遷移ルール（唯一の遷移手順）

**すべての phase 変更はこの手順で行う**（承認リセットの phase 戻しを含む）。playbook 側は「Step 6 を実行（次 phase: X）」とだけ指示する。commit や報告を playbook 側で重複して行わない。

1. `docs/hotl.state.json` を更新: `phase` を次へ、`phase_history` の現エントリに `completed_at`、次エントリを追加、`updated_at` 更新
2. `reporting.md` の書式で報告文を作成し、log.md に追記する
3. git repo なら関連成果物を commit（メッセージ: `hotl: <旧phase> -> <新phase>`。`repo` が `"parent"` なら親リポジトリへ）。**対象は docs/ 配下（`docs/inbox.md` を除く）・`.gitignore`（初回遷移）・そのフェーズの成果物ドキュメントを明示的にパス指定する。実装ループの WIP は含めない。`git add -A` は使わない。`git add -N .`（intent-to-add の一括指定）も使わない — 追跡対象を汚し、`git status` が実態を誤って見せる**（実装ループ中断時の WIP を巻き込まないため）
4. 報告文をユーザーへ送る（届け方は reporting.md）

**ターンを終了してよい場面**は次のみ:

- `hearing`: 質問の返信待ち
- `awaiting_approval`: 承認待ち
- プロジェクト特定・ブートストラップ・環境の自己修復での確認（Step 2 の新規確認・不正状態の退避確認・対象プロジェクトの確認 / Step 3-1 の docs/ 衝突確認・3-2 の入れ子リポジトリ確認）
- `done` 到達時の最終報告、および done 済みプロジェクトへの短い応答（Step 5）
- 状況確認クエリへの応答（Step 5。**ターンの起動メッセージが状況確認だった場合に限る** — 作業中に届いた状況確認は reporting.md 割り込み 0 で答えて続行する）
- 停止指示への応答（reporting.md 割り込み case 1）
- 検証タスクを除く全残タスクが人間の入力（API キー等）待ちでブロックされた場合、および受け入れ検証のキャップ超過（05）

`specification` / `design` / `development` は自律区間であり、上記以外ではフェーズ完了後そのまま同一ターン内で次フェーズの playbook を Read して続行する。自律区間から承認リセットで `requirements` に戻った場合も同様に、同一ターン内で 02 を続行しゲート再提示（`awaiting_approval`）まで進める。`done` からイテレーションで `hearing` に戻った場合も、同一ターン内で 01 を Read し差分ヒアリングの質問まで進める。

**委譲実行モードの例外**: 起動プロンプトが hotl-pm からの委譲で「区切りで戻る」を指示している場合、その区切り（定義は委譲プロンプトに転記された hotl-pm の定義が正。転記が無ければ同じ `.claude/skills/` 内の `hotl-pm/SKILL.md` Step 4 を Read する。個別のブロッカーは含まない: タスク分離して続行する。Step 2 / 3 / 4 の人間確認〔不正状態・docs 衝突・入れ子リポジトリ〕が必要になった場合は cannot-continue として返す）**もターン終了が許される場面に加わる**。このとき「同一ターン内で続行」は適用しない（続行は hotl-pm Step 4 の受領規則に従う）。

## Step 7: 割り込みと途中介入

ユーザーの指示が来たら**共通手順「人間の入力の経路」**で処理先を決め、`reporting.md`「割り込みへの対応」の手順に従う（停止指示以外で作業を止めない。要件レベルの変更だけは承認リセットでゲートに戻り、ここだけはブロックする）。
**ターン実行中の割り込みに限らない**: 作業途中のプロジェクト（`done` 以外）への新しいターンの起動メッセージが、単なる再開語ではなく指示・依頼・変更を含む場合も同じ経路で扱う（処理を始める前に trail へ `interrupt` として記録する。記録の type は修正依頼・質問も `interrupt`）。
