# 安全装置 導入計画（2026-08）

human-on-the-loop の土台（唯一の承認ゲート・承認後の自律性・state/git からの再開・成果物中心のコンテキスト分離・単純な状態遷移）を維持したまま、品質・安全性・可観測性を強化するための調査結果と導入計画。

**ステータス**: 承認済み（2026-08-29）。実装範囲は **B-1〜B-6**（B-7 は保留）。コードレビュー頻度はタスク毎（省略条件付き）、BLOCKED は「不可逆・外部影響・秘密情報」に限定。B-1〜B-6 実装済み。

## 2. 不足している要件

1. **実装コードの独立レビュー**が無い（実装ループはセルフレビューのみ。要件・受け入れに比べ、コードだけ fresh context の目を通らない）
2. **決定論的な検証ツールチェーン**（formatter / linter / 型検査 / ビルド）の選定・実行が工程に組み込まれていない（テストのみ）
3. **指摘・問題の3分類**（自律修正 / バックログ / BLOCKED）の明文規則が無い。BLOCKED の報告書式も無い
4. **証拠ルール**（推測だけを根拠に完了しない）が明文化されていない
5. **タスクの進行中表示**が無い（着手中タスクが tasks.md 上で判別できない）
6. リポジトリ全体の**横断監査**（古い参照・正本重複・未完了指摘の棚卸し）が節目に無い

## 3. 既存機能の拡張で対応できる要件（新しい役割・ファイルを増やさない/最小限）

- **Code Reviewer** → 既存の「fresh context レビュー」パターンの適用。checklist-requirements.md と同型の `checklist-code.md` を1枚追加し、05 実装ループに1ステップ挿入
- **決定論的検証** → design.md テンプレートに「検証ツールチェーン」節を追加（技術選定と同時にツールを選定）。05 の commit 前チェックを「テスト」から「ツールチェーン一式」に拡張
- **3分類 + BLOCKED** → reporting.md にトリアージ規則と BLOCKED 報告書式を追加。BLOCKED は Step 6 の既存項目「人間の入力待ち」に該当する状況の**分類名＋報告書式**（許可リスト自体は変更しない）
- **証拠ルール** → 05 のチェック＆commit 手順に「証拠（実行結果・テスト出力）を trail に記録してから `[x]`」を追加
- **進行中表示** → tasks.md 記法に `[>]`（進行中）を追加し、完了時に完了時刻を行末に付記
- **横断監査（System Reviewer）** → 最終受け入れ検証と同じ fresh context パターンで、done 前に1回の「整合性監査」を追加（チェック観点は checklist に持たせず 05 に直書き。項目が少ないため）
- **コンテキスト管理の強化** → SKILL.md エージェント構成節に読み込み規律（無条件の全読み禁止・要約優先）を1項追加

## 4. 新しい仕組みが必要な要件

- **排他制御（ロック）** のみ。既存機構では代替できない。ただし §6 のとおり選択可能機能とし、実装は保留

## 5. 導入しない方がよい機能（理由）

| 機能 | 不採用理由 |
|---|---|
| 実行契約の12項目/タスク | タスク粒度は半日以下（05）。12項目の記帳はタスク本体より重くなり P7（Lean）違反。目的・入出力・開始条件はフェーズ（playbook）レベルで既に定義済み。採用する核は「検証方法を含む完了条件」と「証拠ルール」のみ |
| 秒単位の所要時間記録・タスクヘッダーの状態集計 | 進捗の正本は tasks.md のチェックボックス（D6）。ヘッダー集計は正本の重複（設計原則「状態遷移の正本を複数作らない」に抵触）。開始・完了時刻は trail と行末付記で足り、所要時間は導出可能 |
| 遠隔通知インターフェース | 現段階で通知の送り手が存在しない。「正本はファイル、通知は読み直す契機のみ」という境界原則は PRINCIPLES のアンチスコープに記録済み。実装はしない。現行ワークフローは通知ゼロで成立している |
| 毎タスクのシステム監査・実装開始前監査 | 03/04/05 の双方向検算が同じ欠陥クラス（残骸・参照切れ・カバレッジ漏れ）をフェーズ遷移ごとに検査済み。監査の追加は done 前の1回で十分。頻度を上げるのはコストに対して効果が小さい |
| レビュー専任の常設エージェント定義（.claude/agents） | 既存のサブエージェント呼び出し（playbook 内の入力リスト指定）で同じ分離が得られる。定義ファイルの追加は配布単位を複雑にする |

## 6. プロジェクトごとに選択可能にすべき機能

- **排他制御**: 単一セッション運用（現状の主用途）では不要。state.json に `"lock": {"enabled": false}` を持たせ、有効時のみ動作:
  - **取得条件**: 作業を伴う起動の Step 4 冒頭で `docs/hotl.lock` を作成（内容: セッション識別子・`date` による時刻）。**状況確認クエリ（読み取り専用）では取得しない**。既存の非 stale ロックがあれば取得せず、所有セッションを表示して停止する
  - **更新（heartbeat）**: フェーズ遷移（Step 6）と各タスクの完了 commit のたび、および長いタスクの途中の節目（テスト実行後など）にロックの時刻を更新する。更新なしにロックを長時間保持しない
  - **解放条件**: ターンを終了するすべての場面（Step 6 の許可リストに列挙された各終了時点）で、自セッションのロックのみ削除する
  - **異常終了時の回復**: ロックの**最終更新時刻**が閾値（既定 8 時間 — タスク粒度の上限「半日」より長く取る）より古ければ stale とみなし、取得し直してよい（trail に `decision` として記録）
  - **所有者不在の判定**: stale 判定と同一（時刻ベース。プロセス生存確認はサンドボックス越しに信頼できないため使わない）
  - **誤解除の防止**: 自分の識別子と一致しない**非 stale** ロックは削除禁止。人間に報告して指示を仰ぐ（stale なら上記の回復手順で自律取得してよい）
- **コードレビューの省略条件**: 数行の機械的変更（typo・定数変更）はレビューをスキップ可（既定はタスク毎に実施）

## 7. 推奨する最小構成

B-1（コードレビュー）+ B-2（決定論的検証）+ B-3（3分類・BLOCKED・証拠ルール）。
この3つで「コードだけ独立レビューを通らない」「機械で検査できるものを AI が目視する」「人間へ上げる基準が暗黙」という現状の最大の穴が塞がる。B-4〜B-6 は次点、B-7 は保留。

## 8. 複雑化のリスクと回避策

| リスク | 回避策 |
|---|---|
| レビュー層の増加で自律区間が遅くなる | コードレビューは1タスク1回・1周まで（指摘の自律修正後の再レビューで打ち切り。収束しない指摘は3分類でバックログ or BLOCKED へ） |
| Human-in-the-loop への後退 | BLOCKED の発動条件を「**不可逆な操作・外部への影響・秘密情報（API キー・課金等）**」に限定 — 05 の既存ブロッカー規則の一般化。設計レベルの変更は現行どおり**自律処理**（design.md 更新＋trail 記録して続行。04/05/P1 の既存規定）であり BLOCKED にしない。承認済み要件を無効化する変更は BLOCKED ではなく既存の**承認リセット経路**（ゲート再実行）で扱う |
| 正本の重複 | 新しい状態ファイルを作らない。追加はチェックリスト1枚・既存ファイルへの節追加・tasks.md の記法拡張のみ |
| 全部入りテンプレート化（P7 違反） | 検証ツールチェーンは「カテゴリと導入方針」だけを design.md に書き、具体ツールは技術選定時に決める |

## 9. 段階的な導入順序

1. B-3（3分類・BLOCKED・証拠ルール）— 他の全レビューの土台になる分類規則を先に定義
2. B-1（Code Reviewer）— 分類規則の最初の利用者
3. B-2（決定論的検証）
4. B-4（進行中表示・完了時刻）
5. B-5（done 前の整合性監査）
6. B-6（読み込み規律の明文化）
7. B-7（排他制御）— 複数セッション運用が実際に始まるまで保留

各ステップ完了ごとに PRINCIPLES の変更プロセス（fresh レビュー → 修正 → PASS まで）を回す。

## 10–11. バックログ

各件は独立した変更として実行・検証できるが、**B-1 と B-5 は指摘の処理規則として B-3 を前提とする**（§9 の順序どおり B-3 を先に導入する）。

### B-1: 独立 Code Reviewer
- **目的**: 実装コードを作成者と別コンテキストでレビューし、欠陥の早期検出と一貫した品質基準を得る
- **範囲**: `playbooks/checklist-code.md` 新規作成（観点: 関連仕様・設計との整合／正確性と境界条件／責務分離／命名・可読性・処理粒度／重複・マジックナンバー・過剰コメント／エラー処理と復旧／セキュリティ・入力検証・インジェクション／性能・不要処理／後方互換性／テスト十分性／運用性・保守性）。05 実装ループのセルフレビュー後に「fresh context レビュアーに **diff・関連 S-n の仕様抜粋・design.md の該当モジュール節・checklist** のみを渡す」ステップを挿入（観点はこの入力で検査可能な範囲に揃える。要件との整合は S-n 経由とトレーサビリティ検算が担保）。指摘は B-3 の3分類で処理
- **対象外**: レビュー専任エージェント定義の新設。1タスク2周以上のレビューループ
- **完了条件**: 05 と checklist-code.md が上記を定義し、レビュー省略条件（§6）が明記されている
- **検証方法**: フレームワーク変更プロセス（fresh レビュー）で、逐語実行時にレビューが実行・分類・修正まで一巡することをシミュレーションで確認

### B-2: 決定論的な自動検証
- **目的**: 機械で検査できる品質項目（整形・静的検査・型・テスト・ビルド）を AI の目視から排除する
- **範囲**: templates/design.md に「検証ツールチェーン」節（formatter / linter / 型検査 / 単体・統合テスト / ビルド / セキュリティ・依存検査 の各カテゴリについて導入するか・何を使うかを技術選定時に決める）。04 の進め方に選定ステップ、05 のチェック＆commit を「ツールチェーン一式を通す」に拡張
- **対象外**: 特定ツールの固定。CI 設定の生成（プロジェクトの要件になった場合のみ）
- **完了条件**: 設計時にツールチェーンが選定され、05 が commit 前にそれを実行する規則になっている
- **検証方法**: fresh レビューでのシミュレーション＋サンプルプロジェクトのドライランで commit 前にツールが走ることを確認

### B-3: 指摘の3分類・BLOCKED・証拠ルール
- **目的**: 「何を自律修正し、何を後回しにし、何で止まるか」の判断を明文化する
- **範囲**: reporting.md に3分類と BLOCKED 報告書式（背景／選択肢／各影響／推奨案／根拠）を追加。05 に証拠ルール（実行・テスト・一次資料で検証し、証拠を trail に記録してから `[x]`。推測だけで完了しない）
  - **① 既存ルール内で低リスク・可逆** → 自律修正＋検証＋再レビュー
  - **② 今のタスクの完了には不要だが、承認済みスコープ内の欠陥** → tasks.md に優先度・理由・完了条件付きで登録（挿入位置は最終受け入れ検証タスクの直前。「関連:」は該当 S-n、無ければ「指摘」と明記）。**スコープ外の改善はこの分類ではなく既存の proposal 経路**（trail 記録 → 最終報告で採否を人間へ）
  - **③ 完了に必須で、不可逆・外部影響・秘密情報に関わる人間判断が必要** → BLOCKED。**Step 6 の許可リストは変更しない**: BLOCKED は既存の「人間の入力待ち」に該当する状況の分類名＋報告書式であり、指摘1件で停止せず、現行どおり該当タスクを分離して他タスクを続行する（全残タスクがブロックされた場合のみターン終了）
- **対象外**: BLOCKED 用の新しい phase・新しいターン終了条件（state・Step 6 は現行のまま）。設計レベルの変更判断（現行どおり自律処理）
- **完了条件**: 3分類・書式・証拠ルールが記載され、既存の指摘処理箇所（要件レビュー・受け入れ検証）が同じ分類を参照している（要件レビューは承認前・tasks.md 不在のため①/③相当のみ。②の対応物は 02 既存の「3周で収束しなければゲートで開示」）
- **検証方法**: fresh レビューで、(a) API キーが必要な指摘 → ③でタスク分離、(b) リファクタ指摘 → ①で自律修正、(c) スコープ外の機能追加提案 → proposal 経路、に正しく落ちることをシミュレーションで確認

### B-4: タスクの進行中表示と完了時刻
- **目的**: tasks.md を見ただけで「いま何が進行中か・いつ終わったか」が分かるようにする
- **範囲**: tasks.md 記法に `[>]`（進行中。着手時に付け、完了で `[x]`）を追加し、完了時に行末へ `（完了: YYYY-MM-DD HH:MM）` を付記（`date` から取得。commit 時刻から導出可能な情報の意図的な重複 — 一覧性のため。進捗の正本はチェックボックスのまま）。templates/tasks.md と 05 を更新。再開時の「先頭未チェック」判定は `[>]` を最優先で拾う。**バックログ整合の削除分岐に `[>]` の扱いを追加する**: 進行中タスクの要件が削除された場合は WIP の破棄/引き継ぎを判断して trail に記録した上で `[-]` 化する
- **対象外**: 秒単位の所要時間記録・ヘッダーへの状態集計（§5）
- **完了条件**: 記法が定義され、実装ループ・バックログ整合・再開規則が `[>]` を扱える
- **検証方法**: fresh レビューで `[>]` を含む再開・整合シナリオをシミュレーション

### B-5: done 前の整合性監査（System Reviewer）
- **目的**: 個別検査で漏れる横断的な不整合（古い参照・正本重複・未完了指摘・state/trail/git の食い違い）を出荷前に検出する
- **範囲**: 05 の「最終受け入れ検証」タスクの**手順1として**整合性監査を組み込む（監査 → 受け入れ検証の順で同一タスク内。独立ステップにすると tasks.md に載らず、クラッシュ再開時にスキップされ得るため）: fresh context の監査者に docs/ 一式と `git log --oneline` を渡し、(a) 成果物間の矛盾・古い参照、(b) 未完了の指摘・依頼（trail の finding/interrupt で未処理のもの）、(c) state・tasks・git の整合を確認させる。指摘は B-3 の3分類で処理
- **対象外**: 毎タスク・実装開始前の監査（§5）。フレームワークリポジトリ自体の監査（それは PRINCIPLES の変更プロセスが担う）
- **完了条件**: 05 に監査ステップと監査観点が記載されている
- **検証方法**: fresh レビューでのシミュレーション（意図的な不整合を仮定し検出経路を確認）

### B-6: 読み込み規律の明文化
- **目的**: コンテキスト分離を「渡すもの」だけでなく「読むもの」の規律として完成させる
- **範囲**: SKILL.md エージェント構成節に追記: 各役割は自分の入力リストにあるものだけを読む／docs/ やリポジトリ全体の無条件読み込みをしない／trail・会話履歴は生ログでなく要約・末尾数件で渡す／アーカイブ・過去イテレーションの資料は現在のタスクに関係する場合のみ
- **対象外**: 機械的なアクセス制御（指示ベースで十分）
- **完了条件**: 規律が1節に集約され、各 playbook の入力リストと矛盾しない
- **検証方法**: fresh レビューでの相互参照チェック

### B-7: 排他制御（保留・選択可能機能）
- **目的**: 複数セッションの二重実行防止（§6 の設計をそのまま実装）
- **範囲**: §6 の仕様（lock ファイル・取得/更新/解放/stale/誤解除防止）を SKILL.md に追加し、state.json に `lock.enabled`（既定 false）を追加
- **対象外**: プロセス生存確認・通知・常駐監視
- **完了条件**: enabled 時に二重起動が検知・拒否され、stale 回復と誤解除防止が規定どおり動く
- **検証方法**: 2セッションを模したドライラン（lock ファイルを手動配置して各分岐を確認）
- **着手条件**: 複数セッション運用を実際に始めるとき（それまで実装しない）

## 12. 必要なエージェント・スキル・テンプレート・状態項目

- **新規エージェント定義**: 不要（全レビュー役は既存の fresh context サブエージェント呼び出しパターンで賄う）
- **新規スキル**: 不要（hotl 1本を維持）
- **新規ファイル**: `playbooks/checklist-code.md` の1枚のみ（B-1）

## 13. 人間の判断が必要な事項

1. **この計画の承認と実装範囲**
   - 選択肢: (a) 推奨最小構成 B-1〜B-3 のみ / (b) B-1〜B-6 / (c) 全件（B-7 含む）
   - 影響: (a) は最小コストで最大の穴を塞ぐ。(b) は可観測性・横断監査まで整う。(c) は現状使わないロック機構の保守が増える
   - **推奨: (b)**。根拠: B-4〜B-6 は各1ファイル程度の小変更で恒常的な可視性・規律が得られる。B-7 のみ利用実態がなく保留が妥当
2. **コードレビューの既定頻度**
   - 選択肢: タスク毎（省略条件付き）/ 3タスク毎
   - 影響: タスク毎は検出が早く手戻りが小さいが自律区間が遅くなる。3タスク毎は速いが混入した欠陥の切り分けが難しい
