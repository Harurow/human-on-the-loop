## 1. 欠陥（findings）

### CRITICAL

作業消失・ゲート素通りは発生しなかった。ただし C-2 で **`done` に到達できなくなった**（フレームワークの規定どおりの帰結）。C-1 は条件次第で CRITICAL 相当。

**C-1（CRITICAL 一歩手前 / 実質 MAJOR）: 「タスクの diff をレビュアーに渡す」が新規ファイルで成立せず、`git add -N .` に誘導される**
- 該当: `playbooks/05-development.md` Step 2-5「fresh context のレビュアーに『タスクの diff』…**のみ**を渡して」
- 実行中に起きたこと: T-1・T-2 の成果物はすべて**新規ファイル**（Makefile・tests/・todo.py）で、`git diff` は空。レビュアーに diff を渡すため素直に `git add -N .` を実行した。結果、`git ls-files` に `.claude/skills/hotl/**` 16ファイルが intent-to-add として並び、`git status` が実態を誤って見せる状態になった。
- 素直な解釈: 「diff を渡せ」と言われたら `git add -N` するのが最短。SKILL.md Step 6 は `git add -A` を禁じているが `git add -N` には触れていない。
- 救われた理由: Step 6-3 が「明示的にパス指定」を義務づけているため、実際の commit には混入しなかった（`git rev-list` で全 commit を検査して確認済み）。**もし playbook が `git commit -a` や `git add -A` を1箇所でも許していたら、フレームワーク一式と WIP がユーザーのリポジトリに入っていた。**
- 提案: 05 に「新規ファイルの diff は `git diff --no-index /dev/null <file>` で作る（インデックスを汚さない）」を明記する。

**C-2（CRITICAL）: 全称命題の非機能要件が `done` を到達不能にし、脱出口が非エンジニアへの技術的な A/B/C だけ**
- 該当: `playbooks/05-development.md` 手順4「収束キャップ（検証）: 受け入れ検証は**最大3周**…3周目も全合格に至らない場合… ⚠️ で報告し、ターンを終了する（**done へは遷移しない**）」／`reporting.md`「検証キャップ超過・停止の報告書式」
- 実行中に起きたこと: NR-6「ヘルプ表示と**全**エラーメッセージの文面に、日本語以外の説明文が含まれない」が、3周とも不合格になった。機能要件 R-1〜R-9・NR-1・NR-3・NR-4・NR-5 は周2以降ずっと合格。**不合格は毎回 NR-6 だけで、毎回まったく別の経路**だった:
  - 周1: 保存ファイルが不正な UTF-8（Shift_JIS で手編集・途中で切れた）→ 英語トレースバック。**死んだ例外ハンドラ**が原因（92テスト・4回のコードレビュー・セキュリティレビュー・2周の監査が見逃していた実バグ）
  - 周2: 書き込み失敗（読み取り専用フォルダ・ディスク満杯）、`bulk` の標準入力が Shift_JIS、引数が不正 UTF-8
  - 周3: パイプ切断（`todo list | head -1`）、標準出力の書き込み先が満杯、`bulk` で標準入力が閉じている、非 UTF-8 ロケール（`ja_JP.eucJP`／`ja_JP.SJIS`。どちらも macOS に実在）でのヘルプ
- 構造の問題: NR-6 は**環境側の失敗経路すべてに対する全称命題**である。fresh context の検証者は毎周あたらしい経路を作れるので、**修正しても「残りの経路が有限である」ことを示す手段が無い**。合格経路は毎周増えているのに、判定は毎周 FAIL。
- 帰結: 05 手順4 は「done へは遷移しない」と定めているので、**このプロジェクトは永久に完成しない**。唯一の脱出口は reporting.md の ⚠️ で田中さん（非エンジニア）に A（ヒントを添えて再挑戦）／B（基準を緩める＝承認リセットしてゲートやり直し）／C（別の方法）を選ばせること。
- 田中さんの立場: 「機能は全部できているのに、聞いたことのない状況（パイプ切断・ロケール）のせいで完成しない」と言われる。B を選ぶには**自分が承認した基準を自分で緩める**必要があり、何を緩めれば安全かを判断できない。
- なぜ机上では出ないか: 要件レビューは3周とも NR-6 を「検証可能」と判定した（実際、書式としては検証可能）。**「検証可能」と「有限回で合格を示せる」は別物**であり、チェックリストにこの観点が無い。
- 提案: (1) チェックリスト §3 に「全称・全数を要求する基準は、検査対象の集合を有限に列挙できるか」を追加する。(2) 05 手順4 に「同じ NR が3周とも別経路で不合格なら、基準の書き方の問題として扱い、B（緩和）を推奨として提示する」を入れる。(3) 02 の既定値の例に「ヘルプと**通常操作で出る**エラーメッセージ」のようなスコープ限定の書き方を示す。

**M-8（CRITICAL 相当の設計矛盾）: UX ウォークスルーの「必ず直すべき」に、承認済みスコープ外を扱う経路が無い**
- 該当: `playbooks/05-development.md` 1.5「指摘は `reporting.md` の3分類で処理し（『必ず直すべき』は①または②で検証タスクの直前に挿入）」 ↔ `reporting.md` ②「**スコープ外の改善はこの分類ではなく proposal 経路**」
- 実行中に起きたこと: UX ウォークスルーが「必ず直すべき（done の前に）」を5件返し、その内容が本物だった。ところが5件中**4件が承認済みスコープ外**だった:
  1. 30件あると期限切れが画面上部へ流れて毎回見えない → 表示を絞るには R-2 の受け入れ基準（未完了は全部表示）に反する = 要件変更

- 提案: 1.5 に「必ず直すべきがスコープ外なら、**承認リセット（要件変更）でゲートに戻すか、proposal に落として done を保留するかを人間に選ばせる**」経路を明記する。

## 3. 人間役（田中さん）として感じた摩擦

1. **ドラフト提示（1444文字）が重い。** 「案A/B/C＋機能提案2件＋10節のたたき台」が一度に来る。ターミナルで読むには長く、どこを直せばいいのか探すのに時間がかかる。「違うところを指摘してください」と言われても、全部それらしく見えるので「あとは合っています」と流してしまった。**私はこの一括同意で「（推測）」10箇所以上を無言で承認したことになる。** これは propose-and-confirm の設計上の狙いどおりだが、リスクの高い推測（保存場所・データが消えたときの扱い）とどうでもいい推測（1日10回の想定）が同じ重みで並ぶのが辛い。
2. **承認ゲートの「品質の目安」が判断できない。** 「やること1000件でも一覧が1秒以内」「書き込み途中に電源が落ちても壊れない方式」と言われても、良いのか悪いのか分からない。全部「提案です」と書いてあるので、結局「おまかせ」以外の選択肢が無い。**判断できないものを承認させられている感覚**が残った。
3. **「3回レビューしたが指摘が出続けた」の開示が不安を残す。** 直したとは書いてあるが、何が残っているのか分からない。「細部です」と言われても、素人には細部かどうかを判断できない。かといって指摘の中身（一時ファイルの権限）を見せられても困る。
4. **修正依頼が「1回だけ」で済まなかったら、と思うと怖い。** 「期限を入れたい」という一言で、要件が作り直され、レビューが3周走り、再提示まで待った。次に「やっぱりスマホでも見たい」と言ったら何が起きるのか想像がつかない。**変更の重さが事前に分からない。**
5. **開発中の報告が「T-7 削除 / T-8 一括登録」のようにタスク名で来る。** 何件終わったかは分かるが、**自分が何を得たのか**が分からない。「もう使えるんですか？」と聞きたくなる。
6. **最終報告が2300文字ある。** 05「完了」が要求する項目（何ができたか・最初にあなたがすること・使い方・既知の制限・受け入れ基準の検証結果・非機能横断チェック・UX ウォークスルーの結果・改善提案・凍結中の要件への指摘・却下した指摘）を全部書くとこの長さになる。「行数制限は適用しない（ただし簡潔に）」とあるが、**項目が10個ある時点で簡潔にはならない**。田中さんが実際に読むのは「最初にあなたがすること」と「使い方」だけだと思う。
7. **「いまどうなってる？」への答えが良かった。** 2行で「12件中3件」「いまは一覧表示」「あなたの作業はありません」と返ってきたのは分かりやすかった。ただ、これがフレームワークで保証された挙動なのか、たまたまなのかは分からない（→ M-1）。
8. **「必ず直すべき」と判定されたものが直らないまま完了報告に来る。** UX レビューが「30件あると大事なものが画面から消える」「メモを移すと日付が期限にならない」と指摘したのに、最終報告では「改善提案」として番号付きで並ぶ。田中さんの立場では、**これは提案ではなく「使えない」という報告**に見える。しかも「採用したい提案は番号でどうぞ（短い確認のあと要件に反映し、再度承認をお願いする流れになります）」と書かれるので、直してもらうには**もう一度ゲートを通る**ことになる。
9. **「あなたの作業はありません」は、承認後ずっと言われ続けるので信頼できた。** 承認から完了まで一度も入力を求められず、報告だけが流れてきた。人間役として一番楽だった部分。
10. **最終報告の「最初にあなたがすること」が5行のコマンドで、ここだけ急に難しい。** それまで「あなたの作業はありません」だったのに、最後に `echo 'export PATH="$HOME/bin:$PATH"' >> ~/.zshrc` を打てと言われる。BLOCKED 書式と同じ粒度で書けとは 05 に書いてあるが、**「打てば動く」ことと「意味が分かる」ことは違う**。ここで失敗したら誰にも聞けない。
11. **最初に「何往復かで整理します」と言われたのは安心材料になった。** ただし実際は2往復で、承認まで含めて人間の発話は5回。ここは軽かった。
12. **最後に「完成しませんでした」と言われたのが一番きつい。** 2時間待って届いたのが ⚠️ で、「機能は全部できています。速さも安全も合格です。でも『どんなときも日本語で説明する』という約束が守れないので完成にできません」という報告。しかも直すべき対象が「パイプを途中で止めたとき」「Mac の文字コード設定を古いものにしたとき」で、**田中さんが一生やらない操作**である。A/B/C のうち B（基準を緩める）が正解に見えるが、**自分が承認した基準を自分で緩めろ**と言われており、どこまで緩めれば安全かを判断する材料が無い。「おまかせします」と返したくなるが、A/B/C にその選択肢は無い。
