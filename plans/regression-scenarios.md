# 回帰シナリオ集

**敵対的レビューを回すときは、このファイルをレビュアーに渡し、全シナリオを必ず1回通させる**（新規の探索はその後）。目的は「過去に直した欠陥が、後の修正で壊れていないか」を毎周確認すること — 毎周ちがう fresh context がちがう箇所をサンプリングするだけでは、回帰は原理的に検出できない。

各シナリオの形式: **系列**（何が起きるか）→ **期待**（正しい挙動）→ 出典。
新しく MAJOR 以上が見つかったら、修正と同時にここへ1件追加する。

## A. 承認ゲート

- **A-1 再開語でゲートを素通りしない**: `awaiting_approval` で「続きから」「開発を進めて」「進めて」→ **期待**: 承認と記録せずゲートを再提示（CRITICAL・初期ラウンド）
- **A-2 提示前の同意を消費しない**: ゲート提示 → 修正依頼 → 修正中に「さっきのは承認します」→ 次の起動 → **期待**: 現在のゲート提示より前の発言なので承認にせず「後続指示により陳腐化」を記録して再提示（43周）
- **A-3 編集途中の版を承認しない**: `requirements` 中（修正反映前のクラッシュ後）に「修正込みで承認します」→ **期待**: 承認せず 02「要件定義中の再開」で執筆を完成させてから提示（45周）
- **A-4 本文待ちと承認の取り違え**: ゲートで「修正を依頼する」を本文無しで選択 → 翌ターン「はい」/「続きから」/「やっぱり承認します」→ **期待**: 「はい」は修正依頼扱い、「続きから」は本文でも承認でもなく聞き返しの再提示、「やっぱり承認します」は承認（45・46・47・50周で振動した箇所）
- **A-5 未反映の修正依頼がある間は承認しない**: inbox に「修正依頼」→「承認します」が続けて届く → **期待**: 先に修正を反映してゲート再提示（48周）
- **A-6 承認手続きの途中クラッシュ**: 承認記録 → 記入 → ハッシュ → state の各段で切れて再開 → **期待**: 未実施の手順から続行、承認リセットのエントリを承認と誤認しない（初期ラウンド・50周）

## B. 人間の入力が成果物に届く

- **B-1 承認待ち中の仕様・設計レベルの希望**: 「保存は SQLite じゃなくて JSON でいい」→ **期待**: 修正依頼として requirements.md の前提・制約に反映し、変更点付きで再提示（50周。hearing-notes に書くだけでは下流に届かない）
- **B-2 作業中の状況確認で止まらない**: development 中に「いまどうなってる？」→ **期待**: 1〜2行で答えて**続行**（ターンを終えない。ドライラン M-1）
- **B-3 停止指示の優先**: inbox に停止指示＋ハッシュ不一致 → **期待**: 停止の応答を優先してターンを終える（50周）
- **B-4 取り下げた要望を復活させない**: 2周目で「日次メールは要らない」→ **期待**: 非ゴール節へ理由付きで移し、漏れチェックで再追加しない（45周）
- **B-5 作成者が独断で足した要件を検出する**: ヒアリングに無い要件を執筆時に足す → **期待**: 双方向の漏れチェックが検出し、提案として出所を明示（ドライラン M-4）
- **B-5b 方針変更の反映を失わない**: 「設定は YAML でなく TOML で」→ design.md と tasks.md を更新 → 実装途中でクラッシュ → 再開で WIP を「破棄」 → **期待**: 台帳（docs/）は破棄対象に含めず、更新時に commit 済みなので人間の指示が消えない（51周）
- **B-5c 不具合報告が経路を問わず修正タスクになる**: 「承認します。あと CSV 出力が壊れてる」/ 開発中に「記号入りパスワードで落ちる」→ **期待**: どちらも対応記録を付けずに残し、tasks.md があれば修正タスクを挿入、無ければ 05 Step 1 が拾う（51周）
- **B-6 委譲経由でも矛盾の内容が残る**: 03 が要件矛盾を返す → チャンクが cannot-continue で戻る → PM がメインループで 02 → **期待**: finding の全文が trail にあり反映できる（45・50周）

## C. 検証の周回と done への到達

- **C-1 全合格後のコード変更**: 受け入れ検証が全合格 → セキュリティ①で修正 → **期待**: 周数に関わらず再検証する（47周 MINOR-1）
- **C-2 終わらない再検証**: 全合格の周にセキュリティ MINOR が出続ける → **期待**: 全合格の周の MINOR は②に落とさず「最終報告で開示」に固定し、ループしない（49周）
- **C-3 不合格の数え方**: 不合格2回目 → **期待**: ⚠️ を出さず自律続行（3回目で ⚠️。48周）
- **C-4 既出の不合格を捨てない**: 周1で不合格の基準を不完全に直す → 周2で同じ基準が再び不合格 → **期待**: 「既出」として捨てず不合格として数える（48周）
- **C-5 検証タスクは常に末尾**: 方針変更・②・改変検知でタスクを追加 → **期待**: 未チェックの検証タスクの直前に入り、`[-]` を除く最後の行が検証タスク（43周）
- **C-6 受け入れ基準の変更で再検証する**: NR-1 を「2秒以内 → 1秒以内」に変更（S-n は不変）→ **期待**: 検証タスクを再追記して新基準で実測（50周）
- **C-7 変更が無ければ再検証しない**: 要望の取り下げだけのイテレーション → **期待**: 検証タスクを再追記しない（47周）
- **C-8 UX 見送りで往復しない**: UX のスコープ外必須指摘 → 承認リセット → 「見送って承認」→ **期待**: 起算点にせず、再周で同じ指摘を承認リセットの契機にしない（46周）
- **C-9 全称の受け入れ基準**: 「すべてのエラーメッセージが日本語」が毎周別経路で不合格 → **期待**: 基準の書き方の問題として B（緩和）を推奨（ドライラン C-2）
- **C-11 done 後の不具合修正は再検証を通る**: `done` で「CSV 出力が壊れてる」→ 修正タスク → 実装 → **期待**: 05 Step 1 の整合が検証タスクを再追記し、修正が受け入れ検証・監査・セキュリティを通ってから done（52周。経路表で先にタスクを挿入すると整合が「追加なし」と判断して再追記を落とす）
- **C-12 ⚠️ への A/C 回答で ⚠️ が再提示されない**: 不合格3回 → ⚠️ → 「A: 別の API で」→ 修正 → 検証タスク再着手 → **期待**: その interrupt が起算点になり、キャップが数え直されて検証が再実行される（「入力確認済み」を付けると起算点から外れて ⚠️ を再提示し続ける。52周）
- **C-10 監査2周目の修正**: 監査キャップ到達後に修正 → **期待**: 「未監査の修正」として最終報告に併記（47周）

## D. 再開・クラッシュ耐性

## E. サブエージェントとコンテキスト分離

- **E-1 ガイドコメントの削除**: 03/04 がテンプレートから書く → **期待**: `<!-- -->` と `<...>` を残さない（残ると次回「書きかけ」と誤判定して差分更新がスキップされる。44周）
- **E-2 ID を振り直さない**: 2周目で R-3 削除 → **期待**: S-n を詰め直さず欠番のまま（詰めると現存機能に除去タスクが生まれる。45周）
- **E-3 新規ファイルの diff**: 新規ファイルだけのタスク → **期待**: `git diff --no-index /dev/null <file>`。`git add -N .` を使わない（ドライラン C-1）
- **E-4 「渡す」の範囲**: リポジトリを入力とする役割（監査・セキュリティ・受け入れ検証）と抜粋を渡す役割の区別（45周）
